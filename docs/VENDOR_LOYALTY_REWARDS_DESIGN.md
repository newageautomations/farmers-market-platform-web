# Vendor loyalty rewards

## Four-stage reward editor

The rules form now uses date-only start/end controls, with points and the per-customer limit on the first two-column row (stacked on narrow screens). New start dates use UTC midnight and new end dates use the next UTC midnight as the exclusive backend bound, so the selected end day is included; review displays dates only. Validation follows the backend's bounded integer, exact currency, product-count and date-order contracts. Disabled catalog products/variants cannot be selected. The JSON save adapter explicitly selects supported editable fields and excludes canonical preview URLs and unknown runtime keys.

Known reward validation sentinels are allowlisted under BAD_USER_INPUT in transport and classified as correctable errors with guidance to Reward details or Redemption rules. INVALID_REWARD_FIELD indicates an unsupported payload key; the backend does not identify that key, so the precise field from the reported request cannot be reconstructed from that message alone. Previously, unmapped rejections became generic GraphQL errors and triggered the uncertain-outcome navigation lock. Back and editing now remain available even for uncertain outcomes, with final writes locked until reconciliation; confirmed validation rejections permit correction and retry. Tests cover free-product gating, full-day dates, preserved progress after rejection, safe sentinel decoding and the serialized payload allowlist. No backend, migration, or persistent database changes are made.

The publication confirmation now remains inside the shared Dialog after a confirmed ACTIVE save, with an animated centered checkmark, success text and a Done action. Drafts still close immediately; failed or uncertain saves cannot enter the success state. The animation honors reduced motion. Every step transition locks both scrollbar axes for 450ms, including transitions whose dialog height is unchanged because of viewport limits. Reward catalog statuses omit decorative dots and reuse the product catalog's Farmstand badge contract and active-stock presentation. Existing status labels and lifecycle meanings remain unchanged.

The subsequent scroll/dropdown refinement hides dialog overflow for the 300ms height animation plus a 150ms buffer, restores normal scrolling afterward, and cleans up on navigation/unmount. Heading focus prevents automatic scrolling during transitions. Review facts use scoped margin resets to defeat the vendor workspace's inherited value top margin. Review now reuses SearchableMultiSelect's additive `readOnly` mode: the same input, chevron and options styling as the editable pickers, without checkboxes, text editing, clear actions or selection mutations. Other consumers retain their existing behavior. Reward pickers no longer supply footer search hints. This supersedes the earlier native Dropdown review composition described below. Browser checks explicitly measure fact-row centers and verify scroll locking and release; shared-control tests cover pointer/keyboard immutability.

The refinement pass centers reward card descriptions and uses Segoe UI/system sans for their titles and editor headings. Native radios remain visually hidden to preserve keyboard selection semantics, while the visible selection uses an animated check circle; pointer selection does not show the keyboard focus outline. Card hover gently scales the existing Card. Percentage fields align at the start of the details row, all review badge contents center vertically with fixed 14px icons, and metric labels/values share vertical alignment. The feature animates its containing dialog's measured height on forward/back navigation, with animated tracker connectors and circles and matching directional button arrows. Reduced motion skips the height animation and transitions. No shared primitive or global styling is changed.

The reward creation and edit Dialog now follows the supplied four-stage guide: Reward type, Reward details, Redemption rules, and Review & publish. The first stage composes shared Card and Radio into three selectable options, with existing tag/gift artwork and a percentage glyph. Reward details pairs identity and the existing image library with type-specific Discount amount, Percentage discount (plus its existing maximum), or Free quantity and a required product/variant. The image library retains upload/scanning and ownership boundaries; an inline remove action only clears the local selection. Required points, optional UTC start/end times and per-customer limits live in Redemption rules. Existing date/time precision is retained rather than discarding saved times to match the reference's date-only examples.

The progress indicator is an ordered list with `aria-current="step"`, completed states and focus moved to each new stage heading. The existing checkout progress is commerce-specific, and there is no shared compatible wizard. This reward-only composition and its scoped CSS therefore do not introduce a universal stepper or replace shared primitive designs. Cards, radios, inputs, textareas, actions, badges, image selection and native disclosure behavior reuse existing components. No shared primitive was modified.

Review pairs image/name/description with a definition list of reward facts. Eligible products uses the existing Dropdown containing a read-only list, so users can expand it to inspect every selection without changing terms. Empty discount selections explicitly mean all the vendor's products. Product labels survive search results changing and backward navigation; legacy references not found in loaded catalog pages use the service's existing variant-reference fallback. Save as draft submits `DRAFT`, while Publish reward submits `ACTIVE`; status is chosen only by the final action. The existing parent save controller, permission checks, immutable reward versions and uncertain-outcome write lock remain intact.

The backend's existing fixed-discount minimum rule is preserved: a minimum eligible subtotal greater than the discount amount is rejected. The reference's example of a $5 discount with a $10 minimum is therefore not valid under the current domain contract. No backend, schema or persistent test database changes are required or performed.

Counts represent all current saved Active, Paused (`INACTIVE`) and Archived rewards, independently of the list filters. Draft is available as a status filter. Search matches name and description. ManageOwnCoupon gates create, edit and status commands. Inactive and draft rewards can activate; archived rewards retain their list records and cannot edit or reactivate. Deactivation and archival use confirmation Dialogs and preserve backend version/qualification rules. Uncertain saves prevent repeated writes until the user reloads and checks the outcome.

The existing VendorCategoryService verifies the asset MIME type and vendor channel. Legacy rewards without images render a gift fallback; failed image requests also reveal that fallback. No migration, persistent-database write, seed, or deployment is required.
