# Market-day packing and fulfillment

Implemented locally on October 30, 2026. The requested November 15 preorders were subsequently populated in the existing local demo database. No deployment, migration execution, browser automation or screenshots were performed by this work.

## Implemented behavior

- Vendor Orders now has **Packing & Fulfillment** at `/vendor/orders/packing?occurrence=<id>`. One occurrence selector stays outside the shared Master List / Individual Lists tabs.
- Master packing combines a separate walk-up plan with live eligible preorder quantities. Walk-up quantities are edited only in the shared inventory modal, reached through Add walk-up inventory or the product inspector's Edit walk-up inventory button. Vendors can add catalog variants, edit/remove plans, save partial counts, reduce counts and inspect unit progress. Both master and customer packed counts may exceed required quantities; customer overpacking remains eligible for explicit completion once every item has at least its required units. Master packed counts may exceed current demand and remain visible as, for example, 4 / 3 packed with an Overpacked status. Overall gathered percentage and its meter credit only `sum(min(packed, required))` across variants, divided by total required units. Surplus never inflates this percentage or compensates for a different product that is not yet packed; actual packed counts remain unchanged. Actual gathered units are preserved when demand falls, including when all preorder demand disappears.
- Individual lists search customer names and customer-facing order codes. Customer IDs group multiple orders; orders without a customer ID use their own order identity. Names never establish identity. Each operational line has a persisted, editable packed quantity with partial progress, followed by explicit customer completion and reopening. No checkbox controls remain in the customer panel. Products use the approved native disclosure contract with image, quantity/status and meter in the summary; clicking a product opens its controls and closes the other product. All start collapsed. Open state and input nodes persist across autosaves. The panel shows quantity, product/variant, each item meter and an overall customer meter; repeated pickup/order metadata is omitted from individual items. Product/customer rows use shared clickable RecordCards with plain content and a visually hidden native keyboard target. Product cards show the variant image (falling back to the product image, then the shared store icon) on the left. Every product/customer card has an animated progress meter below its packed count/status. Walk-up inventory opens the shared Dialog. Row dividers are removed.
- Vendor Market Day cards show master status, gathered units, remaining customer lists and an exact occurrence link. A master marked Packed still explicitly shows incomplete customer lists. Empty demand is Not planned.
- Loading, safe errors, save feedback, automatic refresh when returning to the browser tab, quantity validation, cancelled-date read-only behavior and owner/permission checks are included.

## Architecture and UI reuse

Backend additions are `src/plugins/market-operations/packing.{model,entity,service,api}.ts` and migration `1794900000000-VendorMarketPacking.ts` in the backend repository. The existing MarketOperationsPlugin registers the entity, service and admin-only resolver. The migration adds only `vendor_market_packing`, its vendor/occurrence foreign keys, unique scope and occurrence index. Existing inventory, orders, attendance and financial tables are unchanged.

One vendor/occurrence record stores planned and gathered quantities keyed by variant ID, per-line packed quantities and source signatures keyed by operational order-line ID (with backward-compatible reads of legacy full-line checks), and customer completion fingerprints. Reads and writes run inside transactions serialized by a vendor/occurrence advisory lock. Saves require the current revision and a live-source fingerprint. Stale saves fail and the UI reloads authoritative data. Reconciliation preserves actual master quantities, including surplus, and removes invalid customer line quantities/completions after source changes. Repeating an already-applied value with the current revision is a no-op.

Frontend additions are `apps/admin/src/vendor/packing.tsx`, `packing.css`, `packages/api/src/packing.ts`, the generated GraphQL operations and focused tests. Existing vendor service/routing, Orders navigation, schema extraction/codegen and safe-error mappings are extended. The shared AttendanceHistory receives one optional **vendor-only** content slot. The Market Manager Market Day controller, panel, styles and behavior are unchanged.

The page reuses the existing dashboard shell, Tabs, Card, Button, IconButton, Badge, Field, Input, SelectField, Dialog, RecordCard and safe/loading/empty states. A small feature-specific linear PackingProgress composition is needed because the existing shared progress visualization is a circular loyalty ring. Its fill transitions width and color over 350ms, disables motion for reduced-motion users, and uses red below 25%, orange from 25% to below 50%, yellow from 50% to below 100%, and green at completion. The thumbnail is a packing-specific composition over native images and the shared UtilityIcon fallback; the existing POS tile has register-only purchase controls and cannot be reused as an administrative packing row. Save feedback always occupies the same line, with no inserted/removed paragraph during saves; customer availability text also retains its summary line. The sidebar retains its DOM/scroll container and disables scroll anchoring to prevent jumps during quantity updates. No Refresh packing button remains. PackingInspector is a feature composition because AttendanceDetail contains manager-only attendance controls and is not a reusable packing panel. It uses the exact existing `attendance-columns`, `attendance-detail-shell` and `attendance-inspector` contracts: 220ms ease-out opening, 220ms ease-in closing, retained closing content, the same 1100px stacked/mobile layout and reduced-motion rules. Like the reference, this is an inline side inspector with no modal backdrop. Packing adds contained scrolling, heading focus, Escape dismissal and trigger-focus restoration. The individual-list customer inspector uses a 25% shorter maximum height, `calc(75dvh - 4.5rem)`, compared with the master inspector's `calc(100dvh - 6rem)`; it retains internal scrolling and the same responsive behavior. No new primitive, competing styling system or design-category approval is introduced.

## Preorders and status interaction

Only placed, inactive, settled marketplace Seller orders with committed checkout attempts qualify. Their immutable OrderContext and OrderLineLink records must match the current vendor, seller channel, customer order and selected occurrence. A set-based SQL read aggregates physical stock movements for those lines; JavaScript groups customers and variants in one pass.

Remaining packing demand per line is `max(0, min(native quantity, linked quantity - RELEASE quantities) - net fulfilled quantities)`. Net fulfillment follows the existing CommerceTopologyService convention: negative SALE and CANCELLATION quantities. Cancelled/ineligible orders and zero-remaining lines disappear. Collected units no longer require packing. Deleted catalog records retain stable IDs and a readable catalog/ID fallback; new plans require current ownership.

Existing offering sales caps and opportunity commitments describe preorder capacity. They are not walk-up plans and are never added again. **Total required = this feature's walk-up plan + eligible remaining preorders.**

Financial-only refunds deliberately retain any uncancelled physical pickup obligation, matching the existing separation of refunds and inventory cancellation. A refund with unfulfilled cancellation contributes RELEASE movements and reduces demand. Order/line timestamps and movement watermarks invalidate affected quantities/completions conservatively, including same-quantity lifecycle changes. New qualifying lines or orders invalidate customer completion. Increasing a customer quantity through its input/stepper records newly packed units and increases the master gathered count by that delta. Decreasing it corrects only the units that this line previously added to the master; units assigned from existing gathered stock return to the available pool instead. Optional per-line addedQuantity metadata preserves this distinction without retroactively changing older saved counts. Neither view writes stock, reservations, payment, fulfillment, delivery or Ready for Pickup state.

Already-gathered preorder availability is `max(0, master packed - planned walk-up quantity - all current customer packed quantities for that variant)`. Individual cards display the available count and each customer item offers **Use N already packed**. This sets that line's target packed quantity without changing either master packed or required totals. Availability is shared across customer orders and recomputed under the existing vendor/occurrence lock, so the same units cannot be reused twice. Quantity corrections release capacity back to this feature's availability pool; changed source signatures invalidate affected quantities. Ordinary customer quantity increases explicitly represent newly gathered units; the separate Use already packed action consumes the existing pool instead. The pool is packing progress only, not stock or a new inventory reservation.

The new optional JSON progress/source-accounting fields require no database migration. Legacy checked lines retain their full packed quantities and explicit completion status until a relevant source change.
