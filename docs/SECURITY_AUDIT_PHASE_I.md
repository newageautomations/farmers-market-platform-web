## Migration and rehearsal

Both `npm run start:server` and `npm run start:worker` apply pending migrations before starting Vendure. Each uses the existing PostgreSQL advisory lock for the database and schema and TypeORM's `each` transaction mode on the same query runner. A failure prevents that process from finishing startup. The Phase I migration follows `MarketDayStorefront1797700000000`.

I ran Vendure's `generateMigration` on the migrated 3.7 schema using each version's actual plugin configuration, then reviewed the forward SQL. The 3.8 generator emitted 1,527 statements, of which 1,498 were also emitted by 3.7. The shared output included drops and rewrites of custom foreign keys, checks, indexes and historical columns. I excluded the shared drift and kept the 29 additive framework statements. These create `seller_translation`, add asset usage, refund destination, order pricing timestamp, administrator avatar, and API type on sessions and API keys, and install the required indexes, foreign keys and translation uniqueness constraints. Existing asset rows default to `LIBRARY`. Legacy session and key API types start nullable. [Vendure 3.8 schema guide](https://github.com/vendurehq/vendure/releases/tag/v3.8.0#user-content-1-database-migration)

The migration invokes `deduplicateTranslations` before adding uniqueness to the 13 existing translation tables. The new seller table is created with uniqueness. Vendure keeps the most recently updated row for each entity and language. It then invokes `rescaleOrderLinePromotionAdjustments` in the same transaction and deployment, before either 3.8 process serves work. The helper scales only eligible legacy promotion amounts based on order history. Deduplication permanently deletes losing rows and rescaling overwrites the old amounts. The migration's `down()` fails with restore guidance. If the helper reports ambiguous modification and cancellation timestamps, keep traffic paused, reconcile the affected line quantities from trusted records and review the basis before retrying. [Translation deduplication](https://github.com/vendurehq/vendure/releases/tag/v3.8.0#user-content-duplicate-translations) · [Promotion adjustment helper](https://docs.vendure.io/current/framework/reference/typescript-api/migration/rescale-order-line-promotion-adjustments)

The rehearsals ran in a dedicated Docker internal network with an unpublished PostgreSQL 16 container on tmpfs. I verified the container, network, each database name, and empty destinations before migration or restore. The API and worker used separate public-asset and private-document tmpfs paths, generated credentials and synthetic users. Only the rehearsal databases were connected. The Docker build and audit used public registries, and the application had no provider egress. I removed the disposable services, credentials and archive after verification and retained the candidate image locally.

## Owner approval, restore and manual acceptance

1. Select a private staging clone or disposable environment and verify its DB host, database, asset root, encrypted document root, worker destinations and credentials. Use the exact previous and candidate images. Disable outbound providers, stop both previous entry points and pause writes and worker processing before taking a PostgreSQL custom-format dump. Snapshot the corresponding asset and private-document stores. Record checksums, retained encryption keys and restore ownership/grants. Test restoring the archive into a separate empty database before proceeding.
2. On the approved clone, count duplicate translations and review the rows that would be deleted. Check pre-3.8 order lines with `quantity > 0 AND quantity < "orderPlacedQuantity"` and promotion adjustments, and review ambiguous history before cutover. Time the migration against the actual volume, including the database lock and the existing 15-second statement timeout. Start the candidate API with traffic held. Verify 87 migrations on the rehearsal chain, a single Phase I ledger entry, and health. Start the worker, verify a queued job finishes, and then perform the manual checks.
3. At the account origin's `/account/login`, use a dedicated verified vendor owner such as `phase-i-vendor-owner@example.invalid` and select the synthetic vendor. Open the Admin app at `/vendor/settings/profile`, choose **Add picture** or **Replace picture**, and upload a square PNG or JPEG. Expect the preview and saved picture. Refresh and view the asset or a resized variant under the API's `/assets/` route. Try an unsupported file and expect rejection. Repeat sign-in with the dedicated market manager `phase-i-market-owner@example.invalid` and confirm their workspace at `/market/applications`. Existing Admin sessions require a fresh sign-in after cutover.
4. Using the market manager, prepare a published `phase-i-applicant` application with a Documents step and a test insurance request. On the market storefront, open `/apply/phase-i-applicant` as the verified vendor owner, select the synthetic vendor and upload a harmless PNG in **Documents**. Expect Available in the scoped document list. The storefront posts to `/api/application-documents`. Confirm rejection with a signed-out session and an unsupported file. Repeat the separate Admin compliance upload from `/vendor/documents` as the authorized vendor. Verify availability with the environment's approved scanner and confirm private files stay outside the public asset path.
5. As `phase-i-buyer@example.invalid`, open the synthetic vendor's `/products/phase-i-carrots` and `/checkout` with a published `PHASE-I-CARROTS` variant, configured pickup and a known price. On the disposable environment use the local payment fixture or keep collection suspended and check the cart and final quote. Prepare a second verified synthetic buyer and a Market pickup cart for the same last unit. In the local payment fixture exactly one checkout should settle, the winner's payment and order total should agree, and the other should be denied.

If verification fails after the migration commits, keep traffic and workers paused, preserve the failed target for diagnosis, and restore the pre-upgrade archive into a separate empty database. Restore the matching storage snapshots, verify the data and migration ledger, then start the previous API and worker against that restored target. Account for any writes or provider events admitted since cutover before reopening. The schema rollback cannot recover deleted translations or original promotion amounts.
