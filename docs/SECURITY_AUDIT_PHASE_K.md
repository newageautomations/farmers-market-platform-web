On a deployed host, those mappings can make the ports available on host interfaces, with external reachability depending on effective publishing, routing and firewall rules. The reviewed Vendure configuration selects PostgreSQL and a database-backed job queue. Redis appears in the template and its presence in any deployment remains unverified. The template ports are evidence for A-07 and are not approved probe targets. ## Owner checklist for external verification

- **Approve the scope per environment.** Confirm whether the remote demo, staging and production exist and identify the deployed revision if available. Privately supply the exact public HTTPS hostnames, ports, expected published storefront URL and Admin endpoint. Supply the exact Vendure listener address, protocol, port and expected API hostname for direct checks, plus the exact PostgreSQL and Redis hosts and ports if external TCP checks are authorized. Specify the approved external vantage point and request permission for those endpoints. Owner-controlled inspection can supply evidence where an endpoint has no approved external target.
- **Check storefront and Admin through the edge.** Make one GET to the approved published page and confirm expected tenant content through Astro. Confirm the effective dashboard build points at the approved Admin endpoint, then send one read-only GraphQL POST with no Vendure session, such as `query PhaseKAdmin { activeAdministrator { id } }`. Use the actual approved dashboard origin when the browser sends it. In the gated demo, a separately authorized gate-only session can get the request to Vendure. Confirm explicit denial or the expected null result with no private data. Inspect `data` and `errors` even on HTTP 200, and establish that the request reached the Admin API. With a dedicated authorized staging account, repeat the read-only query as a positive control and record only whether it returned the expected account. Authenticated access stays **unverified** until that control is available. [Admin schema](../packages/api/schema/admin.graphql#L4)
- **Check the direct Vendure listener independently of the edge.** Review the deployed upstream destination, listener, TLS or origin authentication, firewall and trusted proxy/header policy. From the approved external vantage point, perform one bounded connection or agreed read-only request to the exact known listener, with TLS SNI and HTTP `Host` set to the expected API hostname where applicable. Record network refusal or filtering, successful TCP with TLS or origin-auth rejection, or an identifiable Vendure response. An application 403 or 404 shows Vendure was reached. Corroborate a timeout with effective network rules or firewall evidence before marking network isolation verified.
- **Confirm private route exclusions and webhook rules.** Inspect active path and method rules for `/shop-api`, `/customer-account-bridge`, and the two Stripe paths above. For the two private routes, if approved, send one benign request each through the approved public ingress and correlate the response with the edge decision or upstream logs. Use a read-only query for raw Shop and no operation or credentials for the bridge. Record where each request stopped. A gate or upstream application denial alone leaves edge exclusion unverified. Check webhook host, method, path, upstream and body handling from configuration only.
- **Confirm the data-service boundary.** Inspect each deployed service's effective bind, publishing or load-balancer rules, firewall, and private-network scope. If explicitly authorized, make a single TCP connection attempt per exact known host and service port from the approved external vantage point, then close it without authentication or data exchange. A successful connection is **unexpectedly reachable** for a private service even if authentication is required. A deployment inventory confirming Redis is absent supports **not applicable**. Retain only the timestamp, vantage-point description, environment, route or service, observed layer, and disposition. Keep response bodies, credentials, cookies and full infrastructure exports out of the report.
