# Dynamic hosted storefront routing

Farmerlane can serve vendor and market storefronts on new first-level hostnames without changing Railway variables or Cloudflare routes for each store. An authorized owner claims an address in the existing Website library. Vendure commits the storefront and its registry assignment together. Astro reads that assignment and its current publication state on each request.

## Routing and security

- The named Cloudflare Tunnel forwards the browser authority to loopback Caddy. Caddy handles the exact Admin, API, and account authorities first. Only the exact API authority can reach API ingress, with `GET`, `POST`, or `OPTIONS` on `/admin-api` and `GET` or `HEAD` on public `/assets/*`. Admitted storefront authorities go exclusively to Astro. The gateway preserves the HTTPS check, strips incoming forwarding and private transport headers, and supplies the service credential and Cloudflare client address.
- `explicit` accepts only `STOREFRONT_PILOT_HOSTS`. `dynamic` also accepts eligible first-level DNS labels under `STOREFRONT_PARENT_DOMAIN`. The gateway rejects dynamic mode with Access ingress and rejects ports, trailing dots, nested hosts, and unrelated domains as storefront authorities. A syntactically valid but unknown or ineligible storefront gets a generic 404 from Astro, including requests for shared static files. The API still accepts SSR only on its private authority with the SSR credential.
- A new claim trims and lowercases ASCII input. It accepts 1 to 63 letters and digits separated by single hyphens, subject to the DNS name length limit. It reserves `admin`, `api`, `auth`, `www`, `app`, `account`, `assets`, `media`, `static`, `cdn`, `mail`, `support`, `status`, `docs`, `billing`, `payments`, `staging`, `production`, `dev`, `healthcheck`, `ingress`, `gateway`, configured infrastructure hosts, and names beginning with `staging-`, `production-`, `dev-`, or `xn--`. The only reserved-name routing exceptions are the configured exact `staging-vendor` and `staging-market` pilots under the selected parent. The registry still requires an active matching assignment. Those labels remain unavailable to new claims. The existing database constraints and transaction protect uniqueness across markets and vendors, and assignments remain immutable.
- Vendure resolves the exact registry hostname to the storefront ID, business, eligible channel, canonical HTTPS origin, and committed publication snapshot. Astro checks the canonical origin and passes that result to SSR in request-local storage. Public pages and account endpoints require publication. The unprivileged preview frame can load for an unpublished eligible store and render a draft only after a grant check. Staging `robots.txt` and shared build assets carry no tenant snapshot.
- Only `/vendor/storefront` and `/market/storefront` gain the HTTPS parent-domain wildcard in Admin `frame-src` in dynamic mode. The static Admin server has no registry identity when it serves those documents, so CSP alone permits other HTTPS subdomains of the parent. The preview destination comes from the registered storefront, the preview allows framing only by the exact Admin origin, and Vendure checks the grant's stored principal permissions, storefront, website, host, and expiry on render. Astro also checks the returned storefront ID. Preview documents and rendered drafts are `no-store`.
- Central sign-in validates customer destination origins against the hosted hostname policy and exact active, published registry entries. The existing handoffs bind the destination origin, storefront ID, and correlation state. Host-only cookies, exact origin checks, Admin-only API CORS, and provisioned tester admission continue to apply. Use `/account/login` for an existing staging account.
- The existing publication transaction updates the public snapshot and its version atomically. The next request reads the committed snapshot. Astro holds no cross-request storefront or negative lookup cache. SSR, drafts, private account responses, and unknown-host responses use `private, no-store`. Only shared fingerprinted build assets retain their existing immutable browser caching. Keep the Cloudflare staging cache bypass.

## Cloudflare and deployment order

1. Record the healthy Railway release IDs, variable settings, and current Cloudflare Tunnel, DNS, WAF, rate limit, and cache rules. Verify the existing named Tunnel, active Universal SSL certificate for proxied first-level subdomains, HTTPS enforcement, TLS minimum, and exactly scoped infrastructure rules. Inventory exact DNS names that belong to other services before expanding any zone-level rule. [Cloudflare subdomains and Universal SSL](https://developers.cloudflare.com/fundamentals/manage-domains/manage-subdomains/) · [Wildcard DNS precedence](https://developers.cloudflare.com/dns/manage-dns-records/reference/wildcard-dns-records/)
2. Deploy the reviewed API release first with the pilot compatibility list, then the Admin and Astro releases, then the gateway release. Apply the variables above and verify private readiness and the existing five exact public routes before opening wildcard traffic. Check staging login, the two pilot storefronts, both preview contexts, API ingress restrictions, gateway readiness, and connector readiness. [Existing staging verification](STAGING_PUBLIC_INGRESS.md)
3. In **Security → WAF → Custom rules**, edit the existing staging sensitive-path block or challenge rule. Replace its five-host staging selector with the expression below, keeping the existing path and method predicates, action, and ordering. Keep API-only conditions pinned to `http.host eq "staging-api.farmerlane.com"` and any Admin-only conditions pinned to `http.host eq "staging-admin.farmerlane.com"`. If the zone inventory finds a first-level host outside this staging topology, append `and not (http.host in {"<existing-unrelated-host>"})` within the staging selector with the actual exact hosts. Preserve current zone WAF and DDoS settings. [Custom WAF rules and Free limits](https://developers.cloudflare.com/waf/custom-rules/) · [Rules operators](https://developers.cloudflare.com/ruleset-engine/rules-language/operators/)

   ```text
   (http.host wildcard "*.farmerlane.com" and not (http.host wildcard "*.*.farmerlane.com"))
   ```

4. In **Caching → Cache Rules**, replace the staging cache-bypass host expression with the same selector and exact exclusions, if any. Set **Cache eligibility** to **Bypass cache** and ensure a later matching Cache Rule cannot make these requests eligible. The expression includes the three infrastructure hosts and both pilots. A response may report `DYNAMIC` under bypass. [Cache rule settings](https://developers.cloudflare.com/cache/how-to/cache-rules/settings/)
5. Keep the existing `/api/account` rate-limiting rule and its action, threshold, counting characteristics, and mitigation duration. Free-plan rate-limiting rules support Path and Verified Bot fields. An existing path-only rule, such as `http.request.uri.path eq "/api/account"`, already covers the wildcard hosts. Keep any existing trailing-slash or bot conditions. If an existing rule on a plan that accepts Host contains the storefront pilot list, replace only that predicate with the selector above. Preserve any intentionally central-only scope. Application rate limits still govern storefront account traffic. [Rate-limiting fields by plan](https://developers.cloudflare.com/waf/rate-limiting-rules/#availability)
6. In Cloudflare One, open **Networking → Tunnels → existing named Tunnel → Routes → Add route → Published application**. Enter subdomain `*`, domain `farmerlane.com`, blank Path, service type **HTTP**, and URL `127.0.0.1:8080`, giving origin `http://127.0.0.1:8080`. Leave **HTTP Host Header** empty and **Protect with Access** disabled, including inherited per-origin defaults. Keep every existing exact published application above the wildcard in the saved route order. Save the wildcard as the last hostname route, immediately before the terminal `http_status:404`. The Tunnel uses the first match, so verify the order in the saved configuration before acceptance. Keep the existing Tunnel and token. [Published routes](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/) · [First-match ingress](https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/configuration-file/) · [Origin parameters](https://developers.cloudflare.com/tunnel/reference/origin-parameters/)
7. In **DNS → Records**, verify the route created a proxied `CNAME` named `*` (`*.farmerlane.com`) pointing to `<existing-tunnel-UUID>.cfargotunnel.com` with Auto TTL. Add that single record manually if Cloudflare did not create it. Keep all exact records in place. Exact DNS records take precedence over wildcard DNS. Public wildcard traffic can start as soon as the route saves because the dashboard normally adds DNS automatically. [Tunnel DNS behavior](https://developers.cloudflare.com/tunnel/concepts/routing/) · [Wildcard DNS records](https://developers.cloudflare.com/dns/manage-dns-records/reference/wildcard-dns-records/)

If a rollback is needed, remove only the new wildcard route and its wildcard DNS record first. The five exact routes and records stay in place. Set `STOREFRONT_ROUTING_MODE=explicit` on gateway, Astro, and Admin, keep the two pilot values and `STAGING_INGRESS_MODE=application`, then restore the captured edge expressions. Redeploy the prior compatible releases only if needed. Verify the exact routes, sessions, and pilots. Database entries and publication snapshots persist through rollback.

## Hosted staging acceptance

1. Sign in at `https://staging-auth.farmerlane.com/account/login` using the dedicated Cedar Bend Farm owner. Open `https://staging-admin.farmerlane.com/vendor/storefront` with Cedar Bend Farm selected. Confirm the assigned address is `https://cedar-bend.farmerlane.com`. Open its editor and verify the preview loads with Cedar Bend content. Use **Publish** after checking the content. Open the hostname in a fresh private window and verify a signed-out 200 with the correct site.
2. Use an existing dedicated vendor owner with an unconfigured workspace at `/vendor/storefront`. Try `admin` and then `cedar-bend`. Expect the reserved and already-in-use messages. Enable a different address such as `oak-and-ember`, preview it, and verify its public homepage returns 404 until publication. Use a dedicated market manager with an unconfigured workspace at `/market/storefront` to repeat with a distinct market address, such as `juniper-grove` if available. If the available test owners already have assigned sites, use separate account-only fixtures provisioned through the existing Test Data Manager. Verify both new hostnames show their own content immediately after publication with the same gateway, Tunnel and DNS configuration. [Staging account inventory](STAGING_TEST_ACCOUNTS.md)
3. Save a distinguishable draft in either editor. Its preview should show the change and a private window should show the prior published content until a subsequent publication. `https://unregistered-routing-check.farmerlane.com/` should return 404. A draft-render POST with no valid grant or a grant issued for a different storefront should fail.
4. At a published storefront's `/account/login`, use the dedicated existing customer. Complete sign-in through the central account host and confirm the callback returns to the initiating storefront and the customer can open `/account`. Visit the other storefront separately to confirm the first host's session is not carried over. Use `/account/workspaces` on the central account host to verify authorized vendor and market handoffs. Check that `/account/signup` on the central host refuses registration and that the restricted account actions still deny guest creation.
5. Verify `/vendor/storefront`, `/market/storefront`, and central `/account/login` remain operational. Use the existing exact API acceptance checks for `/admin-api` and public `/assets/*`. Verify public `/shop-api`, `/customer-account-bridge`, and `/storefront-context/internal-resolve` return 404 from API and storefront hostnames. Check that staging storefront responses show `private, no-store` and Cloudflare reports `DYNAMIC` or `BYPASS`. [Exact API acceptance commands](STAGING_PUBLIC_INGRESS.md#hosted-acceptance)
