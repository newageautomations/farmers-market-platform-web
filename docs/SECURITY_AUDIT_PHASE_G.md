# Phase G backend release dependency triage

November 18, 2026 · Private engineering report

**Fix before launch.** The release uses end-of-life Node 20. Its public HTTP middleware reaches an affected `body-parser`, and vendor-controlled image bytes reach an affected native `sharp` build. Fix those first. Include the supported Vendure security fixes for administrator and Shop API session separation in the same release candidate. The critical npm entries warrant targeted updates, but the reviewed backend has no identified path to the affected Handlebars or Seroval operations with attacker-controlled input.

## What ships

- Backend revision `75092f15568780770d1d3ba32cf03e53a01de994`. The working-tree `Dockerfile` was modified and `.dockerignore` was untracked before this review. `package.json` and `package-lock.json` matched the revision. Existing source edits included `src/production-http.ts` and identity/contact paths. Reachability uses the working-tree code, including those edits. The lockfile SHA-256 was `cdde4e743e8c028ba6bb70ad343d97a415d00386c478022507cf62a3373ce4ce`.
- The working Dockerfile uses `node:20-bookworm-slim` for `build`, `runtime-dependencies` and `release`. `build` runs `npm ci` and `npm run build:server`. Only `runtime-dependencies` contributes `node_modules` to `release`, from `npm ci --omit=dev`. The final stage also copies compiled server and worker code, `package.json` and the email templates. The dev-only Vendure CLI was absent. Dashboard dependencies including Vite were installed because the dashboard is declared in production dependencies. The API and worker run the compiled entry points.
- Docker Desktop reproduced `linux/amd64` using the tag's resolved image `sha256:2cf067cfed83d5ea958367df9f966191a942351a2df77d6f0193e162b5febfc0`, Node `20.20.2`, npm `10.8.2`, `x86_64`. This is the base resolved for Phase G. Phase F did not record the Node patch and its image was removed. The Phase G dependency-stage reproduction used disposable containers and copies of the two manifests plus local inspection scripts. The releases' application code, project `.env` files, host npm config, registry credentials and customer data were outside those containers.
- The networked install fetched locked public packages from `https://registry.npmjs.org/` with lifecycle scripts disabled. The same install was replayed with lifecycle scripts enabled, the npm cache populated, and Docker networking disabled. Each tree had **1,297 installed package paths**, zero version mismatches against the lock, and zero dev-only paths. The inventory checker read each installed package's `package.json`, cross-checked the count against npm's installed-tree lock, and got the same SHA-256 of the path/version inventory in lockfile order both times (`65bea36ccfe030b7c8e3f3cc3bf5e263d65695b0a6da691ece8d048b84a65fda`). All 100 paths in the audit JSON's `nodes` arrays existed. No full application image was rebuilt. OS and container base-image vulnerability scanning are out of scope. The libraries bundled by the npm `sharp` package are covered here through sharp's advisories.

## Node compatibility

`@vendure/email-plugin@3.7.3 → mjml@5.4.1 → mjml-core@5.4.1 → js-beautify@2.0.3 → nopt@10.0.1 → abbrev@5.0.0`. `js-beautify` declares `nopt ^10.0.1`, and `nopt` declares `abbrev ^5.0.0`. The exact versions of both leaf packages were read from the installed Linux manifests. Each requires **`^22.22.2 || ^24.15.0 || >=26.0.0`**. Node **`20.20.2`** satisfies neither requirement. Both ship in the release.

The `runtime-dependencies` production install emitted both `EBADENGINE` warnings with lifecycle scripts enabled. A separate `build`-stage full-tree `npm ci --dry-run` also emitted both warnings. The final `release` stage copies that dependency tree and runs no npm install. Phase F's prose did not identify which of its stages printed each warning. The install can succeed while the packages' declared compatibility remains unmet, and a prior successful startup smoke test does not change either package's support contract.

The official Node.js schedule ended Node 20 support on **April 30, 2026**. The release page's March 24, 2026 date is its last update. Move all stages to a maintained **Node 24 LTS Bookworm Slim** image, using **24.22.3 or a newer patched 24.x** and recording the chosen `linux/amd64` digest. The current 24.x line satisfies both engines, and the schedule lists support through April 2028. Changing Node versions does not update the npm `undici` copies. Check native `sharp` and `bcrypt`, npm's lifecycle behavior, and the emitted server/worker build.
