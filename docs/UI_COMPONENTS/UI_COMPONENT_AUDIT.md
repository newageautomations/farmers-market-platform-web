# UI component audit

Audit date: 2026-10-12. Repository: farmers-market-platform-web. Phase: documentation only. Source snapshot: the existing local working tree, including its pre-existing uncommitted and untracked work. No candidate is approved by this report.

## Executive summary

The repository already has a substantial shared foundation. This is primarily a reuse, API-contract and CSS-scope problem, not a reason to introduce a new UI library.

- **47 categories audited; 37 contain competing implementations or independently repeated presentation contracts.** The other 10 contain a single implementation or intentionally complementary feature adapters. There are 155 category-specific candidate records. Some index the same definition under different concerns, so 155 is not a count of unique React components or independent implementations.
- **AdminShell already serves platform, vendor and market administration.** CustomerLayout independently recreates its sidebar, topbar, mobile disclosure and content markup in Astro while using the same base CSS. Share presentation across renderers, with isolated role controllers.
- **Shared primitives are adopted unevenly.** Button has 25 direct importing files; Input 18; ErrorState 22. Several exported primitives have no direct application imports. The application also has 125 native button markup sites in 38 rendering files and 44 native select sites. These include legitimate SSR counterparts and specialized controls, not 125 proven duplicate button styles.
- **Concrete behavior duplication exists.** Vendor and Market CommandForm implementations differ in validation recovery and modal lifecycle. Vendor and Market ReadState independently compose the same loading/error/retry UI. Choice/SelectField/Control repeat label/select plumbing.
- **CSS overrides create competing appearances inside shared markup.** Base Card uses 6px radius; dashboard surfaces 10px; layout cards 12px; disclosure cards 14px. Operations raw buttons, plain account actions, designer controls and shared Button have different state/size contracts.
- **Commerce presentation is repeated around correctly separate business logic.** ProductCards and the occurrence offering card, four quantity field implementations, two cart line editors and multiple money-row summaries are candidates for presentation reuse. Preserve separate direct-Vendor and Market cart coordination, tenant isolation, occurrence binding, exact values and payment uncertainty.

Highest priority: select the primitive and surface contracts, formalize existing tokens and CSS scope, characterize modal/command-form behavior, then migrate low-risk display components before shells, mutation forms and purchasing flows. All selections in the root registry remain **PENDING DEVELOPER SELECTION**.

## Regression risks

- **CSS ancestry and order:** removing .ops-workspace/.market-dashboard/.admin-content or moving a component changes hover, height, spacing and focus even if className is identical. Sibling margin rules, dialog sizing, :has designer hiding and default-theme injection are especially sensitive.
- **Form serialization:** shared Button defaults type=button while native form buttons default submit; changing name/id/required/default/disabled changes FormData. Hidden phone E.164 field, unchecked boolean absence, radio vendor grouping, OTP aggregate code and dynamic answers need explicit preservation.
- **State lifecycle:** controlled vs uncontrolled/defaultValue and keyed cart quantities, lazily mounted disclosures, panels mounted/hidden vs conditional, modal timer/unmount and async error feedback can reset drafts or focus unexpectedly.
- **Commands:** two CommandForm recovery policies differ. Do not drop uncertainty locks, UUID stability, revision checks, cancellation confirmations or failure-open editor behavior. Phase14Routes resolves undefined after a refusal; local editor success detection must continue checking it.
- **Authorization and tenancy:** no shared shell/card may introduce cached role authority, cross-tenant reads or stale content after Channel/host/session switch. Preserve current service lifetime/cleanup and backend enforcement.
- **Money/status meaning:** exact formatMoney values, invoice minor-unit math, projection currency grouping, original/refunded/remaining vs checkout total and paid vs fulfilled must stay separate. A colored badge cannot establish successful payment, stock reservation or publication.
- **Purchasing:** Market carts are occurrence-bound and grouped by Vendor, with coupons and cart event count updates. Direct carts have another DTO/line URL/totals shape. Checkout stages and local payment eligibility cannot be simplified into generic tabs or UI-derived confirmation.
- **Accessibility/responsive:** breakpoint overlaps, long labels/currencies, scroll tables, hidden navigation/disclosure controls, tooltip trigger sizing, modal focus and canvas alternatives require browser review beyond static type/lint tests.
- **Rendering:** keep SSR content/no-JS forms/native navigation, Astro island hydration, private/no-store customer pages and context-specific asset/theme safety; do not import Admin controllers into public bundles to share CSS.
