# UI component migration plan

First-round decision date: 2026-10-12. Second-round approval date: 2026-10-13. This is documentation and planning only. No application, styling, test, package, build, authentication, API or purchasing code is changed by this task. Each implementation phase requires a separate instruction; this plan does not authorize starting consolidation.

The authoritative decisions are in [UI_COMPONENTS.md](../UI_COMPONENTS.md), supplemented by [second-round decisions](UI_COMPONENT_SECOND_ROUND_DECISIONS.md). The [audit](UI_COMPONENT_AUDIT.md) and [gallery guide](UI_COMPONENT_GALLERY.md) remain historical evidence and must not be rewritten to imply that migration has happened. Earlier recommendations do not override the developer's selections. Existing local work must be preserved.

## Boundaries and phase sequence

Implement Phase A first, then Phase B, then Phase C; follow with Phase D's separately scoped second-round batches in their dependency order. Within a phase, complete one bounded batch and its checks before expanding to another consumer group. Retain compatibility exports until their consumers have migrated. A category match alone does not justify replacing a source file or merging feature logic.

Every phase must preserve native form names, values, submitter behavior, required/optional constraints, controlled/uncontrolled state, accessible names, keyboard behavior, responsive layout, existing theme boundaries and security contracts. Preserve backend authority, tenant/session isolation, grant enforcement, money formatting, operation intent/idempotency, revision checks and uncertain outcomes. Presentation work must not become a checkout, account, command-form or data-service refactor.

Use existing tokens, shared styles and installed frameworks. Do not introduce a UI library, styling system, production dependency, routing surface or deployment work. New components/adapters must explain why the existing export or renderer is insufficient. The React/Astro renderer difference is a valid architectural reason for thin markup adapters sharing one presentation contract.

Proposed new paths below are planning targets, not files created or final export API commitments. Prefer extending the existing Button/Input/Card exports where suitable. Use a pure render-neutral helper, proposed as `packages/ui/src/presentation.ts`, for shared classes/variants without importing React, admin-core, auth, services or API clients just to style Astro markup. An explicit `@market/ui/presentation` export would require a narrowly scoped future change to `packages/ui/package.json`, not a dependency installation. This fits the existing package boundary checks.

## Phase A: Shared foundations

Dependencies: the eight recorded design approvals and existing source/gallery evidence. There is no dependency on a new backend, credentials or seed data. Phase B/C consumers must not migrate ahead of the foundation contracts they need.

For buttons, retain BTN-01's safe current `type="button"` default. When replacing an implicitly submitting native form button, explicitly preserve `type="submit"`, name/value and the intended submitter. Do not turn navigation anchors into buttons or treat a disabled prop as native anchor disabling. Preserve pressed password/designer/disclosure behavior while standardizing its appearance; button approval alone does not select toggle behavior or tab presentation; TAB-01's separate second-round decision is implemented only in its bounded Phase D batch.

INP-02 currently uses native labeled fields and shared/account CSS. Adopt its appearance without blindly applying React inference to every existing Astro field. INP-01 still calls `inputContract`; preserve its explicit overrides and existing bounds. Keep field-specific attributes and label/error associations. Do not broaden the focus correction to textarea, checkbox, radio, select, canvas or other unselected controls through a global reset. Ordinary field borders remain in their unfocused design; remove the additional gray focus treatment. Choose a non-border background/label indication that also remains perceivable under forced colors, without layout shift or loss of disabled/read-only clarity.

Keep INP-03's native OTP structure and verification controller. Preserve six digits, whole-code paste, first-digit complete-code allowance, arrow/backspace navigation, hidden aggregate code, one-time-code autofill, constraints and verification/resend behavior. Do not replace its digit fields with a generic wrapper that changes inferred lengths/names. `apps/storefront/src/lib/phone-verification.ts` is a protected behavioral dependency to inspect/test, not a planned presentation rewrite. No SMS/account action is needed for visual testing.

SEL-03 currently hardcodes `required` and accepts only name/label/children. Generalization must allow existing required and optional consumers to retain their behavior and controlled/uncontrolled/native attributes. SEL-01 may remain the low-level native Select implementation under SEL-03 presentation. SEL-02 retains its specific color-coded function and feature-owned status labels/mapping; status colors are not universal business truth.

SEL-07 currently prepends a selectable `{ value: '', label: placeholder }` option, and its CSS gives selected, active and hovered options the same green treatment. Remove instructional content from the selectable/keyboard option set, or render it as noninteractive instruction outside that set. It must receive no selection or hover highlight. Keep actual values and selected `aria-selected` meaning intact. Ordinary hover must match SEL-03's neutral slightly darker white/off-white treatment; green belongs only to a committed selected option. Provide a separate visible non-green keyboard-active indication with valid `aria-activedescendant`, filtering, Enter/Escape/blur behavior and appropriate announcements. Optional callers may need an explicit clear mechanism; resolve that without making an instruction row selectable or silently changing business associations.

CRD-02 is a family, not an existing shared Card export. Its representative rules use a white surface, 10px radius, clamp padding, 1.25rem block spacing, border/shadow and min-width containment. Extract that approved contract into existing tokens/styles rather than copying each selector into more callers. Preserve theme boundaries, semantic article/section/li/fieldset structure and feature content. Avoid double padding/margins when converting nested cards or record lists. CRD-01's Card API can remain with the approved surface; CRD-03/05 specialized content and state are not discarded.

For CRD-04, the original toggle is inside `.market-disclosure-header`, with text and chevron in one flex button and a separate optional action. Give the complete clickable heading region comfortable horizontal padding on both sides in its default geometry, so hover reaches past the first letter and chevron without adding padding or changing width on hover. Do not include a separate action button in the toggle hit area. Use BTN-01, including an appropriate explicit disclosure presentation variant, instead of a competing raw-button appearance. Preserve `aria-expanded`/controls, closed-content inertness, lazy mount, grid animation, reduced motion and layout preview/action behavior. Comparable saved-layout disclosure use cases retain the approved CRD-04 scope. The separate second-round DDN-03 approval governs ordinary disclosures, including nested surfaces; coordinate extraction with Phase D without changing CRD-04's approved specialist appearance or earlier fixes.

### Risks, testing and review

Principal risks are changed submit defaults; lost anchor semantics; inferred bounds replacing existing native constraints; disabled-fieldset differences; forced-colors keyboard visibility; controlled select resets; empty-value association changes; CSS specificity/cascade differences; native select popup differences; double card spacing; disclosure click-area changes; and theme leakage from admin CSS into storefront/customer pages.

Future focused tests should cover meaningful contracts: FormData including submitters, native GET navigation, explicit native props/constraints, controlled/uncontrolled behavior, disabled/loading locks, accessible labels/errors, pointer versus keyboard focus at computed-style level, OTP paste/aggregation/navigation/autofill with intercepted synthetic endpoints, specialist selection and listbox semantics, and card/disclosure geometry. Proposed new tests are `tests/ui-foundations.test.tsx` and `tests/e2e/ui-foundations-fixture.spec.ts`; no test files are created by this planning task.

Run relevant existing `tests/admin.test.tsx`, `tests/vendor.test.tsx`, `tests/management.test.tsx`, `tests/market.test.tsx`, `tests/signup-passwords.test.tsx`, `tests/phone-input.test.tsx`, `tests/market-application.test.tsx`, `tests/phase15.test.tsx` and `tests/layout-library.test.tsx` during implementation. Reuse the unchanged isolated gallery for actual component/CSS comparison; it deliberately excludes the live OTP script, so it cannot prove OTP functional parity by itself. Account and purchasing regressions must use existing mocks or an explicitly scoped local test environment, not real mutations.

Manual routes: gallery `http://127.0.0.1:4343/` for BTN/INP/SEL/CRD; read-only fixture `/vendor/products`, `/market/settings`, `/market/vendors`; public `/products`; account `/account/login`, `/account/signup`, `/account/settings`, `/account/verify`; specialist `/market/application-submissions`; surfaces `/market`, `/market/layouts`, `/market/applications`. Account/OTP and operations routes need suitable synthetic state or their existing harness; ordinary FixtureAdmin does not supply every phase14 grant/service. Do not create accounts, resend verification, purchase, save or publish to review appearance.

Completion criteria: reusable contracts/adapters exist; each migrated batch has a before/after behavior and visual record; ordinary appearances match the approved sources/corrections; all four retained specialists keep their functionality; native values/validation and theme boundaries remain correct; no context silently restyles an approved control; relevant checks pass; legacy styles are removed only after their callers migrate. ## Phase B: Dialog consolidation

Dependencies: completed Phase A button/input/select/card contracts and a verified dialog lifecycle characterization. Keep FRM command-form and confirmation business policy categories pending; this phase does not merge their controllers.

### Bounded implementation sequence

1. Characterize DLG-01 and DLG-02 against the same synthetic caller before extracting either lifecycle. Test initial open, close button, Escape/cancel, `dialog.close()`, parent-controlled close, unmount during animation, rapid close/reopen, repeated close requests, focusTitle, busy state, beforeClose veto, long scrolling, nested confirmation use and reduced motion. Record callback counts/timing and trigger restoration.
2. Extract the DLG-02-based native implementation into shared UI, proposed as `packages/ui/src/dialog.tsx`, while preserving `Dialog` and `Drawer` exports in `packages/ui/src/index.tsx`. Add missing necessary capability and fix lifecycle inconsistencies before consumer rollout. A temporary market re-export/compatibility wrapper may delegate to the shared foundation; it must not maintain a second implementation.
3. Migrate vendor/common and inventory dialogs first, then the storefront occurrence preview. Migrate market command/relationship dialogs next, then operations editors and large layout confirmations. Finish one consumer batch with tests before expanding. Retire DLG-01's independent implementation only after all necessary capabilities/callers are covered.

The shared foundation retains native `<dialog>` labeling/focus trapping, DLG-02 animation, busy protection, beforeClose policy and focus restoration. Bring forward drawer presentation and necessary focus-title/width/scroll behavior from DLG-01/callers. DLG-02 currently lacks native `onClose` and ignores its declared `focusTitle`; DLG-01's native close listener and controlled close effect can produce different callback paths. Define and verify appropriate once-only callbacks for accepted close paths and distinguish controlled state changes from user close requests. Do not bypass busy/veto rules or discard drafts just because a timeout completes. Preserve return focus after closing animation; handle unmount/rapid reopen cleanup without stale timers.

Move reusable modal animation/size styles out of market-only ancestry into shared styles with explicit necessary variants. Keep caller-specific editor geometry/content constraints as documented compatible variants. Shared UI cannot import `apps/admin`, admin routes, services, market domain state, auth or permission helpers. Do not move the whole presentation module: its status mappings, search selector and disclosure concerns have their own scopes.

## Phase C: Dashboard consolidation

Dependencies: Phase A foundations complete and Phase B dialog consumers relevant to shell/editor integration verified. DSH-01/SID-01/HDR-01 retain their first-round approvals. MOB-01 and scoped SCH-03/SCH-01 now have separate second-round approvals with pending Phase D work; PGH, NAV and AMC remain pending. Phase C extracts shell presentation without implementing those later category batches or merging their independent controllers.

### Bounded implementation sequence

1. Extract role-neutral dashboard frame, sidebar and topbar presentation, proposed as `packages/ui/src/dashboard.tsx`, plus a shared render-neutral class/layout contract in `packages/ui/src/presentation.ts`. Existing AdminShell remains the React role/router adapter. Move only the approved common styling from role CSS; do not load the whole admin stylesheet/module graph into customers.
2. Integrate the shared presentation with internal dashboards in separate vendor, market and platform batches. Leave `visibleNavigation`, `routeAllowed`, context bootstrap, role permissions, services, URL history and logout in their current application layers. Preserve collapse/inert/current-route/focus behavior and necessary full-screen layout handling.
3. Create a thin Astro presentation adapter, proposed as `apps/storefront/src/components/ui/DashboardFrame.astro`, using the same shared contract and explicit sidebar/topbar/main slots. Refactor CustomerLayout's independent presentation through that adapter while retaining Astro SSR, native CustomerNavigation anchors, customer content and POST logout. Customers must not import AdminShell/AdminApp, admin-core privileges or administrative services to gain consistent visuals.
4. Align the full-screen designer header to HDR-01's visual language using compatible action/status/selection slots and Phase A atoms. Retain its dedicated editor layout, area selection, undo/redo, saving/publishing/version and dirty-state workflows, permission checks and map behavior. Do not replace it with an ordinary page heading or duplicate the outer topbar/h1.
5. Verify desktop and responsive coexistence across roles. Preserve existing mobile navigation and its focus/visibility behavior during shell extraction; reserve the explicitly approved MOB-01-based right-aligned hamburger, MOB-02 appearance replacement and mobile action relocation for the bounded Phase D mobile batch. Provide compatible mobile slots without duplicating production actions or implicitly harmonizing breakpoints.

Shared presentation takes display data/slots and presentation callbacks, not AdminContext, privilege decisions, account/session tokens or API services. Theme values are supplied by the existing caller theme boundary. Route-to-icon and role-navigation mappings stay in adapters; if pure SVG presentation is extracted from NavigationIcon/Chevron, it must not carry admin route/security logic into the shared UI. Customer-specific icon mapping may need review, with no new icon library.

CustomerLayout currently contains normal anchors, customer-specific topbar links and a POST `/api/account` logout form. Keep that mechanism, hidden logout action and form behavior intact with an explicit submitting BTN-01 presentation adapter. The React admin logout callback remains its current mechanism. No session bridge, channel switching, authorization, account API or customer projection logic moves into the shell. Keep customer follow-feedback/busy behavior and server-rendered content in their existing role layer.
