# Product category taxonomy Phase B

## Implementation summary

Vendor product management now assigns one canonical leaf category and predefined, category-applicable tags. The catalog shows canonical parent and child navigation, distinct Product counts, and an Uncategorized filter. Legacy custom category management is removed from the vendor workspace and navigation. No backend code, migrations, persistent database records, or taxonomy definitions were changed.

The existing taxonomy audit was read for Phase A contracts and was not edited by this implementation. Pre-existing local edits to that audit and the retired seed scripts were left intact.

Backend operations reused unchanged:

- `productCategoryHierarchy`: supplies all standardized roots and descendants, IDs, active state and assignability.
- `applicableProductTags(categoryId)`: supplies predefined tag IDs, groups and seller-declared status.
- `ownProductClassification(productId)`: supplies authoritative primary category, hierarchy path and selected tags.
- Existing `createOwnCatalogProduct` and `updateOwnCatalogProduct`: save `primaryCategoryId` and `tagIds` together with the rest of the product metadata in one mutation.
- Existing publication read and publish mutation remain in use. The UI checks classification before allowing the publish mutation; backend publication validation remains final authority.

`setOwnProductClassification` is not needed for ordinary product-form saves because the existing complete-form mutation already supports both classification fields. The legacy category API remains available to unchanged appearance/image consumers, but vendor product management no longer calls its category list/save/delete operations. Backend rejection of legacy category mutations is unchanged.

## Architectural decisions

The picker is a feature composition of the existing Dialog, Field, Input, Radio, Button, Alert, native disclosure presentation, and SearchableMultiSelect. The shared flat SearchSelect cannot expand branches, so it could not supply the hierarchical interaction by itself. No new primitive, UI library, CSS system, or design approval was introduced. The dialog is portaled outside the product form so typing or choosing a category does not submit that form. Shared responsive dialog sizing and dashboard shell remain in use.

Native disclosures support Tab and Enter/Space expansion; native radio controls provide keyboard selection and checked states. Search matches parent and child labels. A parent match retains its children; a descendant match retains its ancestor branch. The selected path is shown outside the dialog and its branch opens with the checked radio on reopening. Only backend-assignable leaves are offered for selection.

A category change first loads applicable tags. Only a successful response commits the new category and intersects selected tag IDs. Removed names are announced in an Alert. Failed category-change reads leave the old category and tags intact. Saves are blocked while that applicability request is pending. A request sequence guard prevents late responses after unmount from committing state.

Initial hierarchy and existing classification are loaded together. Until that read succeeds, the form omits both classification input fields. Failed reads therefore cannot replace an existing category with null or clear tags. A failed applicable-tags read retains the originally assigned tags and disables editing those options. Enabled-product submission requires a known, valid leaf. An uncategorized draft can be saved. The backend still validates submitted IDs, applicability, ownership and publication.

Catalog category membership comes exclusively from each owned Product's canonical `categoryPath`. Parents include descendant products; leaves include direct assignments. Classification is keyed once per Product, so variants cannot inflate counts. Category labels are supplied by the backend without translated-name matching. Empty branches are omitted. Catalog classification reads run in batches of at most eight concurrent requests using the existing authorized operation; no broader backend projection or permissions were added.

## Implemented and excluded scope

Implemented: single-category selection and search, full hierarchy labels, predefined grouped tags, tag addition/removal, compatibility pruning with feedback, canonical create/edit/details, draft and enable validation, a publication precheck, hierarchical catalog filtering, distinct Product counts, and removal of vendor custom-category controls.

Intentionally excluded: market storefront aggregation, public vendor storefront navigation, theme category images/order/visibility, manager customization, POS migration, global taxonomy administration, certification verification, and all other Phase C work. Certified Organic and other claims remain seller declared. Existing storefront appearance image controls and POS behavior were not migrated.

## Known limitations and later work

Manual desktop/mobile visual acceptance and native browser focus/arrow-key behavior remain for the tester. DOM tests exercise keyboard activation and selection semantics but do not replace native-browser review.

The existing vendor catalog loads its full owned catalog for local search/filtering. Canonical classification currently adds one authorized read per Product with concurrency bounded to eight. A future performance-focused contract could provide a bulk classification projection if needed for very large catalogs. A failed catalog classification batch shows the existing read error/retry state rather than inventing Uncategorized assignments.

Phase C remains unimplemented. Later work can migrate public vendor/market taxonomy navigation and aggregation, storefront presentation controls and images, manager customization, and POS category consumers within separately authorized scope. No hosting, publication deployment, remote Git change, or external service was used.
