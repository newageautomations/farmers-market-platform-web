# Farmerlane demo data portability audit

**Phase A · November 26, 2026.** Inspected the two local checkouts, the loopback `vendure_demo_market_ops` database in verified PostgreSQL read-only transactions, and the local Vendure public asset directory. Hosted conclusions come from the checked-in runbooks, implementation, and supplied staging state. Live staging occupancy, release compatibility, and routes remain dry-run checks. This audit produced no export package and made no database, storage, provider, or infrastructure changes.

## Trial recommendation

Use a small hybrid import. Start with fresh trial instances of **Cedar Bend Farm and Juniper Grove Farmers Market** plus a fresh customer. Keep their existing vendor-to-market scenario by recreating one application, confirmed membership, a few upcoming dates, and one published layout with sample booth placements. Add **Willow & Grain Farmstead** to the same trial for a richer public shop and vendor dashboard. Its catalog, illustrated editorial storefront, and pickup data have the clearest reusable fixture sources. Limit the first release to these three workspaces, three owners, and one customer. Approve the public names, branding, venue text, and photos before packaging.

Use a new cohort namespace, unique fixture emails, and new approved host labels. The named staging runbook already reserves candidates for Cedar Bend and Juniper Grove under the legacy pilot hosts. Treat any matching live staging account, business, or route as occupied until the new dry run proves ownership. **Manna Roots and the manager-run Boerne Farmers Market are the richest second-wave candidates.** Require business and brand review and take only their approved catalog, public design, and selected market operations. Their private files, messages, and financial history are outside the trial. [Named staging accounts](STAGING_TEST_ACCOUNTS.md) · [Dynamic storefront routing](DYNAMIC_STOREFRONT_ROUTING.md)

## Portability architecture and package

| Approach | Fit |
| --- | --- |
| A. Fixture reproduction | Lowest cost for deterministic accounts and supported synthetic scenarios. The catalog script's fixed local inputs and the saved website/layout changes prevent faithful full reconstruction from scripts alone. |
| B. Selective export | Best fidelity for approved saved configuration, but requires converters for typed IDs, nested content, assets, and service invariants even when a good generator exists. |
| C. Hybrid, recommended | Extend the existing Test Data Manager release tooling and compile fixture definitions and approved read-only exports into one import format. Reuse the same validator and apply stages for both sources. Preserve existing database and R2 state through scoped additive domain commands. |

Use a strict JSON manifest plus a directory or archive of approved image originals. Proposed fields are `schemaVersion`, `packageId`, `revision`, `source` (fixture generator and/or reviewed snapshot label and code revision), runner compatibility and supported template/taxonomy versions, `trialAnchorDate`, and typed collections for `accounts`, `businesses`, `catalog`, `assets`, `markets`, `websites`, and `relations`. Use references such as `vendor:willow`, `variant:willow/spinach-family`, `occurrence:juniper/saturday-1`, and `booth:juniper/east-a03`. Include synthetic account names, portable SKU/slug input, category codes and parent references, USD minor units, opening stock, and explicit draft/public state. The approval record pins the normalized manifest digest, sorted asset digests, and deployment mapping. Reject unknown fields, duplicates, unresolved or cross-owner refs, unsupported versions, missing required media, and unapproved URLs. Use typed serializers and explicit field allowlists, especially for application, layout, and website JSON.

Exclude passwords and hashes, authentication methods and sessions, verification/recovery/invite tokens, API and provider credentials, encryption keys, provider mappings and transaction references, payment details, unapproved personal information, production data, unapproved private files, and environment-specific secrets. Keep packages, digests tied to private operations, and credentials in operator-restricted storage outside Git. A sanitized manifest may reference approvals by identifier without embedding the approval notes.

For the first cohort, pass a bounded, reviewed manifest or independently validated manifest parts to the temporary Railway service in service-scoped sealed variables, following the named-account spec pattern. Confirm the size budget before relying on inline transfer. Keep image bytes on the operator workstation for the authenticated upload step below. For a larger future batch, use an approved restricted artifact store with a short-lived read grant scoped to an encrypted bundle. Seal the grant and decryption material on the job, verify the pinned digest, unpack into ephemeral storage with path and size limits, and expire/delete the transfer after acceptance. No PostgreSQL public endpoint or new public application route is required.

## Public media

The configured local root is backend `.demo-market-operations/assets`. All 120 checked asset rows resolved to source and preview files beneath it. The original sizes matched database metadata and the originals had PNG/JPEG signatures. This was a file-presence and header check. Individual approval, decoding, metadata review, and nested reference validation remain export work.

Resolve originals from Vendure asset IDs or parse known local URL formats back to owned asset rows. Enforce canonical containment, reject traversal and symlink escapes, and report unknown URLs or missing/invalid sources and previews. Store only approved bytes under portable names, with owner and purpose, MIME, size, SHA-256, approval/license reference, and logical aliases. Hash the final transferable bytes after removing unapproved metadata. A source can be shared in the local database across several channels. Deduplicate within the target tenant by normalized hash and policy, and avoid adopting unrelated assets by filename or hash.

Use a real authenticated staging owner session in the correct channel and the admitted Admin mutation for the use case (`uploadOwnStorefrontImage`, `uploadOwnBusinessProfileImage`, `uploadOwnVendorCategoryImage`, or native `createAssets` where the actor has its normal permission). The job has no uploader session. The current media exception is scoped by `StagingAdmissionInterceptor`, fixture audit, and resolver context, and the worker cannot enable it. Perform uploads through a supervised operator step using existing Admin/API ingress and the unchanged guards. Transfer asset IDs and a verified digest receipt back to the job. Qualify the actual vendor/market upload path for catalog and layout images early. The job should verify each receipt against destination MIME, channel membership, and the asset record's usable source and preview, then apply normal profile, product-gallery, website, or layout references. Vendure generates previews and uses the existing R2 adapter in `farmerlane-staging-media`; its conditional writes protect existing keys. Where a resolver cannot be safely replayed after an ambiguous response, stop and reconcile the specific asset in the owner library before retrying. [Hosted media guard and storage](HOSTED_FILE_STORAGE_PHASE_C.md#upload-authorization-and-file-status)

Record confirmed asset results before binding. Use deterministic names where the existing upload accepts them and persist the target asset ID with owner and digest. Verify the hosted original through existing Vendure asset reads where available. If the supported upload normalizes the original, qualify that transform and record both input and stored digests. After failure, reuse confirmed owned assets and escalate ambiguous uploads for review. The normal importer performs no deletion. A separate authorized cleanup may remove only demonstrably import-created, unreferenced assets through the normal lifecycle after checking owners, references, byte digests and uncertain commits. Leave existing R2 objects intact. If private files are later approved, use authorized plaintext retrieval and the destination's ordinary validated upload, encryption, and grant workflow, with a new approval and access review. The source ciphertext and key stay out of the package.

## Railway job and recovery

1. Run a reviewed release artifact in a temporary staging service, one replica, restart **Never**, with automatic deployments and public networking disabled. Use the private PostgreSQL DNS and restricted `market_staging_runtime` role. Reuse checks from `src/test-data/database.ts`, `src/hosted-database.ts` and `scripts/inspect-staging-files.cjs` for staging service identity, explicit opt-in, `market_staging`, `public`, database marker, PostgreSQL version, private addresses, role and complete release ledger. Keep schema synchronization, automatic migration and queue/scheduler startup disabled for the job. Avoid application bootstrap in dry run.
2. Implement connected `--dry-run` in a read-only transaction. Validate compatibility, remaining prerequisites and package digest, resolve prior provenance, report new/matching/drifted rows and occupied keys, and list pending manual media approvals. Emit logical keys, status and counts only. For `--apply`, require the reviewed digest and explicit operator intent. Recheck live state, take a namespace lock, and let domain uniqueness constraints protect races. Use only ordinary runtime grants and existing account authorization. [Private Railway job precedent](FOUNDATIONAL_COMMERCE_CONFIGURATION.md#private-railway-job) · [Read-only inventory precedent](HOSTED_FILE_STORAGE_PHASE_C.md#inventory-and-preserve-existing-files)
3. Commit bounded stages. Use existing provisioning and command idempotency keys. Persist package namespace, record key, normalized input digest, entity type/ID and stage via `DurableWorkService.audit`, in the mutation's PostgreSQL transaction. Extend `TestDataAccounts.seed` to record account package ownership inside its existing authorized transaction. Asset receipts commit separately. After an uncertain commit, reread provenance and domain state before retrying. Matching input and ownership skip without rewriting tester edits. Changed input, ownership, or missing dependencies block the affected stage. A fresh namespace is required for a new cohort, and updates require separate authorization. Verify audit retention and lookup behavior before considering a separate provenance table. No schema migration is expected for the first release.
4. Inspect and verify using logical-key summaries and normal entry points. Repeat the same apply to confirm zero new accounts, stock, assets, occurrences, or publications. Reject a synthetic cross-tenant reference and hostname collision in disposable qualification. Check existing hosted row sets, provider state and published storefronts through scoped read-only comparisons before and after apply. Keep the deployment ID, manifest digest, sanitized result and recovery state, then remove the job and its variables. Perform live acceptance only with operator authorization.
