# Phase A security audit of the Farmers Market Platform

**I would hold live payment collection and the use of the checked-in backend Dockerfile for a release build.** This revision explicitly rejects live Stripe mutations. The Dockerfile copies the repository into the application image, and Git tracks a backend `.env` file. Its contents and any exposure of real credentials are unverified. I would also keep arbitrary Shop GraphQL traffic off the public edge until the market query parser has a work limit. Two legitimate storefront operations have a separate launch problem: the production guard rejects the requests Astro constructs for vendor contact submissions and applicant document uploads.

The strongest tenant controls I traced were on vendor order portions, customer purchases, financial exports, and private document downloads. Each illustrates an important distinction in this platform: a channel selects a workspace, while a current grant, record owner, or explicit sharing relationship authorizes access. I did not establish a cross-tenant disclosure on those paths. The vendor multipart path and a server-side image-fetch path remain material exceptions to validate.

## Threat model

The main confidentiality assets are customer identity and purchase history, vendor finances, applicant answers, private document bytes, unpublished storefront content, and account capabilities. The main integrity assets are memberships and delegated grants, order attribution, Stripe destination accounts, invoice balances, refund journals, and notification recipients. The API process, worker, scanner, database connections, and recovery queue are availability assets.

The modeled actors are an unauthenticated visitor, a customer with their own session, an unrelated vendor or organizer, a restricted employee, and a formerly authorized user retaining an old session. A release artifact reader is relevant to the container finding. None is assumed to possess a Stripe signing secret, production shell, database administrator role, or another user's session.

## Prioritized findings

### A-01. The backend release image can include the tracked environment file

**Confirmed in source. Severity high. Confidence high for artifact inclusion under the supplied build path.**

Git tracks `farmers-market-platform/.env`. I verified the filename only. In a normal build using the repository root as context, the single-stage Dockerfile copies that file and the rest of the context into the application image. I found no checked-in Docker ignore file. A clean checkout is sufficient for the tracked file to be included. A local working directory can contribute additional files. The affected principals are builders, registry readers, and anyone able to inspect an image layer. Whether an image was built or pushed, whether the file contains usable credentials, and who could read it are **not assessed**.

**Launch decision:** use an allowlisted release context and verify the image file inventory before release. Have the operator privately classify the tracked file and prior artifacts. Rotate any real credential shown to have entered an accessible artifact. [Backend Dockerfile, lines 1, 5 and 7](E:/coding/farmers-market-platform/Dockerfile:7)

### A-02. Market Shop query admission has no bound on fragment traversal work

**Confirmed in source. Severity high if raw Shop queries are externally reachable. Confidence high for the code path.**

A caller who can submit a query for an active market channel reaches a synchronous selection collector before the business resolver. It revisits shared fragment definitions, accumulates field names, and checks the allowlist after collection. It detects cycles but has no total traversal or expanded-field budget. The earlier HTTP guard bounds query text length and rejects JSON batches. Neither bounds the work this collector performs for an accepted document. The sensitive effect is CPU and memory consumption in the shared API process. Outage duration and external reachability are unverified. The named-operation Astro bridge materially reduces public exposure if it is the only route to Shop.

Bound traversal before collection, reuse validated fragment results, and reject over-budget operations before business work. Monitor rejected operations and API event-loop delay. [Middleware registration](E:/coding/farmers-market-platform/src/plugins/platform-identity/platform-identity.plugin.ts:92) · [Public channel resolution](E:/coding/farmers-market-platform/src/plugins/platform-identity/public-storefront.controller.ts:125) · [HTTP input limits](E:/coding/farmers-market-platform/src/production-http.ts:121) · [Selection collector](E:/coding/farmers-market-platform/src/plugins/platform-identity/shop-context.middleware.ts:100)

### A-03. Storefront host rejection may not protect the image-fetch endpoint

**Suspected / needs validation. Severity high under direct-origin and permissive-egress assumptions. Confidence medium.**

The production wrapper checks authority syntax. When persisted tenant resolution fails, Astro middleware records the error and continues dispatch. That is safe only if the eventual handler enforces the applicable host policy. The installed Astro production image handler checks remote source allowlists and redirects, but its local-image branch constructs a destination relative to the request origin and passes request headers to the loader. A visitor needs an ingress path that accepts an unapproved wire authority, an active image endpoint, and outbound connectivity to a resulting destination. The potential effects are unintended server-side requests and forwarding of request headers. I did not establish access to an internal service, disclosure of credentials, or a cross-tenant response.

Reject unresolved authorities before dispatching tenant-relative image requests. Verify the actual build's image route, trusted asset origins, and network egress. The storefront-context resolver itself connects to a fixed backend destination. ### A-05. The production guard rejects legitimate contact submissions and applicant uploads

**Confirmed in source. Severity medium. Confidence high.** This is a launch blocker for either workflow if it is promised at launch.

- **Vendor contact.** A visitor on an enabled vendor storefront passes Astro's canonical-origin check. Astro then sends that canonical origin to Vendure because the contact service uses it to resolve the intended recipient. The production guard rejects an origin-bearing Shop request before the service can perform that match. The normal flow therefore loses the visitor's submission. - **Applicant documents.** A signed-in applicant's Astro route creates a Shop multipart upload with channel, preflight header, session cookie, and server bridge credential. The production multipart guard accepts the Admin browser case or an originless bearer case. It has no admission case for the authenticated Astro Shop bridge. The upload is rejected before the applicant's permission, file type, or scanner result can determine acceptance. [Applicant route](E:/coding/farmers-market-platform-web/apps/storefront/src/pages/api/application-documents.ts:59) · [Upload headers](E:/coding/farmers-market-platform-web/packages/api/src/document-upload.ts:26) · [Bridge and cookie](E:/coding/farmers-market-platform-web/apps/storefront/src/lib/shop.ts:32) · [Multipart guard](E:/coding/farmers-market-platform/src/production-http.ts:114)

Give these two server-to-server operations an explicit authenticated contract. Preserve the canonical tenant-to-recipient match and the post-parse applicant upload restriction. A global relaxation of Shop origin or multipart rules would also affect unrelated operations.

### A-06. Duplicate pending Stripe receipts can enqueue redundant recovery sweeps

**Confirmed in source. Severity medium. Confidence high.**

A genuine signed retry can arrive while its original receipt is still `RECEIVED`. The database transaction deduplicates the receipt by mode and event ID and returns the existing row. Downstream code enqueues a sweep for any returned row in `RECEIVED`. Queue insertion has no corresponding pending-sweep deduplication at this call site. Each sweep can perform work across invoices, checkout, refunds, and webhooks. The affected assets are worker and database capacity, especially during an outage or backlog. **The traced effect is duplicate queued work. I found no duplicate charge or refund from this path.**

Coalesce pending wakeups while retaining the durable receipt and periodic sweep so a lost queue notification remains recoverable. Monitor pending receipt age alongside sweep count. [Receipt lookup and reuse](E:/coding/farmers-market-platform/src/plugins/payments/webhook.service.ts:196) · [Enqueue decision](E:/coding/farmers-market-platform/src/plugins/payments/webhook.service.ts:237) · [Queue insertion](E:/coding/farmers-market-platform/src/plugins/payments/recovery.service.ts:54) · [Sweep stages](E:/coding/farmers-market-platform/src/plugins/payments/recovery.service.ts:103)

### A-07. The Compose database template is unsuitable for a shared or exposed host

**Suspected / needs validation for deployed exposure. Severity high if deployed unchanged on a reachable host. Confidence high about the template, unknown about deployment.**

The checked-in Compose file publishes PostgreSQL on host port 6543 without a loopback address and specifies a literal database password at line 56. Its value is omitted. The same file explicitly loopback-binds the scanner, but also publishes Redis without a host address. A network peer would need routing and firewall access to the host and a usable credential or permissive service configuration for a data effect. Neither public reachability nor successful database access was established.

Separately, API and worker startup both execute pending migrations using `config.dbConnectionOptions`. The migration lock coordinates concurrent startup. It does not separate DDL credentials from runtime credentials. Inspect the actual grants and release procedure before treating a compromised API or worker as a data-only principal.
