# Phase B2 hosted frontend and storefront routing

Phase B2 adds a private Railway transport for the hardened frontend launchers and Vendure. Astro resolves a validated storefront hostname through an authenticated backend request. An operator command assigns hostnames using the existing registry and unique index. The selected topology starts with explicitly listed pilot hosts and uses the existing account, session, storefront publication, and preview authorization logic. Infrastructure provisioning, database release coordination, and external tester admission remain later phases.

## Hosted topology

Use Cloudflare DNS, edge HTTPS, an operator-only Cloudflare Access policy, and a named Cloudflare Tunnel. Run `cloudflared` and Caddy together in one continuously running private Railway gateway service. Use a process supervisor that forwards termination to both processes and treats either process exiting as a service failure. Caddy binds only to `127.0.0.1` inside that service. The connector delivers verified operator traffic to this loopback listener. The gateway reaches the separately hosted Admin, Astro, and Vendure services over private Railway DNS. Keep the worker and PostgreSQL private as well.

This avoids overlapping Railway custom domains on different services and removes any need to treat a public Railway proxy address as a trusted source. The named Tunnel requires a running connector and the Caddy router in addition to the app services. First-level explicit pilot hostnames preserve the eventual storefront URL convention. Validate wildcard registration, Access coverage, and routing separately before expanding the DNS or ingress configuration. [Railway public networking limits](https://docs.railway.com/networking/public-networking/specs-and-limits), [Railway custom domains](https://docs.railway.com/networking/domains/working-with-domains), [Railway private networking](https://docs.railway.com/networking/private-networking), [Cloudflare Tunnel origin parameters](https://developers.cloudflare.com/tunnel/reference/origin-parameters/).

| HTTPS authority                  | Destination                 | Allowed routes                                                                                                                       | Trust boundary                                                                                                      |

| `admin.example.com`              | React Admin launcher        | GET and HEAD for the SPA, its files, and deep links                                                                                  | Operator Access, connector loopback, then Admin-specific ingress key                                                |

The current asset authority is the API host. An additional media hostname is unnecessary in this topology. The future Stripe routes are GET `/payments/stripe/oauth/callback` and POST `/payments/stripe/platform` and `/payments/stripe/connected`. They are outside both the gateway and API hosted allowlists in B2. When later approved, add exact path and method matches, retain the callback state and existing webhook authorization, and forward the original body and `Stripe-Signature` to the existing raw webhook handler. Cloudflare Access preflight handling does not authorize a webhook or an application request.

## Startup and transport

Build the two web apps with `npm run build`. The existing `npm run serve:admin:production` and `npm run start:storefront:production` check the corresponding manifest and client output before listening. Admin retains its SPA fallback. Astro uses its compiled standalone handler, including static-file delivery. In hosted mode both launchers and Vendure accept the injected `PORT` and default to `HOST=::` for Railway private networking. An explicit IP bind is available. Local qualification uses the existing TLS key and certificate paths and loopback listeners. The normal development commands keep their existing transport. Vendure's server and worker entry points retain their current migration behavior pending B3.

The browser connects to Cloudflare over HTTPS. Cloudflare terminates browser TLS and sends traffic through the encrypted named Tunnel. Require the connector's `originRequest.access.required` check and the exact audience and team for each hostname. Require HTTPS at the edge before proxying. Caddy receives HTTP over loopback from the co-located connector and checks for the edge HTTPS, client address, and Access assertion fields. The connector verifies Access JWTs. The presence of a header at Caddy provides a secondary check for a missing connector configuration. Operate the connector and Caddy as one trust boundary and keep the loopback listener inaccessible from other services. [Cloudflare Access validation at the connector](https://developers.cloudflare.com/tunnel/reference/origin-parameters/), [Cloudflare HTTP request headers](https://developers.cloudflare.com/fundamentals/reference/http-headers/).

On the next hop, Railway private networking encrypts traffic with WireGuard. Place all services in the same Railway project environment. Caddy preserves the reviewed wire Host, overwrites its service-specific assertion and client address, and removes incoming forwarding, private API, and Cloudflare assertion headers. Each recipient validates its assertion and rejects ambiguous Host and forwarding headers before processing application traffic. Astro projects the verified HTTPS and client address onto the adapter request. The API keeps Express proxy trust disabled and uses authenticated request metadata for security and rate attribution. Health exceptions return only status. [Railway private networking transport](https://docs.railway.com/networking/private-networking/how-it-works).

The Astro-to-Vendure transport uses an explicitly configured `http://<api-service>.railway.internal:<port>` and a separate SSR credential. The API requires the exact private wire authority and verifies this credential before allowing Shop GraphQL, the existing account bridge, immutable vendor terms revisions, preview authorization, or tenant resolution. Astro uses configured destinations and refuses private fetch redirects. Browser Admin GraphQL, media URLs, and future integration callbacks retain their canonical public configuration. The private keys and destination are absent from public build settings.

Give Caddy a different random 32-byte hex key for each upstream. Give only Astro and the API the distinct SSR key. Keep these separate from the account bridge, cookies, and providers. Caddy disables config persistence and its admin API, and omits request-bearing error and access logs. Rotate one pair at a time during a closed maintenance window. Pause the relevant ingress, replace the key at both endpoints, restart both, verify rejection of the prior key and an authorized new request, then restore traffic. Use the same procedure for the Astro and API pair. Keep the tunnel's own connector credential in the gateway service only.

## Tenant resolution and hostname registration

After gateway and Astro authority validation, Astro sends the selected pilot hostname as a distinct internal resolver input. The API checks it against the platform parent and reserved authorities before using the existing exact registry lookup. Active storefront, subject, and non-default channel eligibility remain part of that lookup. The frontend checks the returned canonical HTTPS origin against the selected tenant. Unknown or inactive storefronts use the existing unavailable behavior. The native resolver remains available to supported local workflows.

Use the guarded operator command from the backend project in a one-off environment that can reach the isolated staging PostgreSQL service. Inject the API staging environment and the operator's PostgreSQL credentials. The database role needs connect, schema usage, read access to the registry ID, key, hostname, and subject columns, and update access on the hostname column. Keep the role internal and limit its use to approved operators. Use `DB_TRANSPORT_POLICY=verify-full` with the approved CA, or the explicitly qualified private database transport. The existing hostname migration `1791230000000-StorefrontPublicHostname` must already be present.

Look up the immutable storefront **key** in the authorized staging registry. Substitute the actual database name, key, and in-domain hostname in one of these commands.

```powershell
npm run storefront:register-hostname -- market_staging vendor vendor-storefront-key vendor-pilot.example.com
npm run storefront:register-hostname -- market_staging market market-storefront-key market-pilot.example.com
```

The command requires the staging identity and a database argument matching the configured database and PostgreSQL's reported database. It normalizes an ASCII hostname to lowercase, accepts one DNS label under the configured parent, and reserves `admin`, `auth`, `api`, `assets`, `www`, `healthcheck`, `ingress`, `gateway`, and configured infrastructure hosts. A same-host retry is idempotent. An existing assignment rejects rename attempts. A row lock serializes assignments to the same storefront and the existing unique index rejects cross-tenant collisions. The command updates only the hostname and performs no migration. Publishing and eligibility are independent. To admit the hostname for qualification, update the exact pilot lists and the connector's operator-only Access rule through the later infrastructure phase.

## Authentication, previews, caching, and health

The public HTTPS URL stays authoritative for central sign-in, workspace selection, callbacks, safe returns, storefront cookies, and origin checks. Existing host-only, Secure, HttpOnly, and SameSite settings remain in effect. The API accepts only the configured Admin origin for browser GraphQL. Shop cookies, channel tokens, account bridge action validation, and durable account limits retain their existing semantics. Trusted client addresses feed the existing rate limits across both paths. Caddy keeps the incoming body and origin intact. There are no changes to communication delivery or payment processing. Staging keeps `STAGING_TESTER_ACCESS=closed` and `STAGING_ANONYMOUS_STOREFRONTS=disabled`. Actual operator admission depends on the edge and connector policy.

Both editor routes load separate Admin documents with an exact `frame-src` list derived from the pilot configuration. Other Admin documents keep `frame-src 'none'`. The preview page and rendered draft allow only the configured Admin origin as a frame ancestor. Astro passes the bounded preview payload through the private Admin GraphQL route. The existing short-lived grant checks the tenant, current permissions, and draft scope. Preview contents are request-local, no-store, and noindex. Initial qualification uses a single Vendure API replica because the preview grant store is process-local.

Astro's dynamic responses, carts, checkout, accounts, documents, previews, and Market Day remain private and no-store. The compiled immutable asset policy is preserved. Use a Cloudflare cache bypass for all pilot traffic until the Phase D rules are reviewed. Stage-wide noindex, restrictive robots handling, and disabled fixture and demo flags continue to apply.

Frontend readiness means the listener opened after validating configuration, manifest, and compiled output. Caddy readiness means its local listener and route configuration loaded. Verify API readiness separately through its existing database-backed endpoint to avoid repeating dependency probes on frontend health requests. Hosted health supports GET and HEAD only with the exact health authority and paths listed above. Native frontend listeners also answer health on their normal TLS authorities. A local gateway probe can use `curl -H "Host: healthcheck.railway.app" http://127.0.0.1:8080/health/ready` from the gateway service. Node stops accepting frontend traffic on termination and bounds draining at 30 seconds. Caddy uses its 30-second grace period. [Railway deployment healthcheck behavior](https://docs.railway.com/deployments/healthchecks).
