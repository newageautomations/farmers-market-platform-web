# SuperAdmin Test Accounts

The Platform dashboard has a **Test Accounts** page at `/platform/test-accounts`. It lists active customer, vendor owner, and market manager identities recorded in the Test Data Manager audit trail, including existing CLI fixtures. The creation dialog accepts custom names, an email ending in `@fixtures.invalid`, a password, and an optional phone number. Vendor owners and market managers get a dedicated workspace and the normal owner role.

A successful submission refreshes the list and supplies a link to the normal sign-in flow. **Copy Login Details** includes the submitted password from the dialog's memory. Closing the confirmation clears that memory. The API returns only account details and the destination. Vendure persists the password hash through its native authentication services.

Vendure's `CustomerService` and `AdministratorService` create the native identities. Vendor setup uses `VendorProvisioningService` and `IdentityService.setMembership`. Market setup uses `MarketProvisioningService` and `MarketService.establishInitialOwner`, with the Test Data Manager's standard America/Chicago timezone and preorder defaults. Personal contact rows carry simulated email and phone verification. The fixture audit records the authenticated SuperAdmin as the actor. An account, its workspace and owner role, the verification, and the audit record commit together.

A blank phone draws from the established US fictional range, 555-0100 through 555-0199, across the configured area codes. Entered phones use the existing international normalization and the personal identity uniqueness constraint. The fixture password policy accepts 11 to 72 printable ASCII characters with an uppercase letter, a number, and a symbol. Ordinary account password rules continue to apply to ordinary signup. The page creates account and workspace records only. The implementation requires no database migration.

## Authorization and environments

- Both operations require an authenticated Vendure SuperAdmin and recheck the principal's current Platform authorization. The backend advertises availability through `platformAdminScope`; the sidebar and direct route use that result.
- Local access requires the existing development target for `vendure_demo_market_ops`, loopback PostgreSQL, the `public` schema, and loopback account and admin origins. The server queries the live database identity before using it.
- Railway staging requires the existing `FARMERLANE_TEST_DATA_STAGING=true` opt-in on the staging API. The server verifies the Railway staging identity, private database transport and connection, the `market_staging` database marker, the runtime role and its restricted privileges, and the PostgreSQL version.
- Production and other targets have no enabled configuration. The list and mutation reject access server-side even with a valid SuperAdmin session.
- Email and phone collisions reject creation. The creation path keeps the existing unified sign-in and stages no email or SMS verification messages.

## Manual testing on the populated demo database

From the web repository, run these commands in four PowerShell terminals. They select the persistent `vendure_demo_market_ops` environment.

```powershell
npm run demo:market-operations:serve
npm run demo:market-operations:worker
npm run demo:market-operations:admin
npm run demo:market-operations:storefront
```

1. Open `http://localhost:4322/platform` and sign in using the existing `demo.platform@example.test` login. Select **Test Accounts** or open `http://localhost:4322/platform/test-accounts`. Expect previously audited fixtures, if present. Established accounts such as Manna Roots and the Boerne Market Manager belong to the ordinary demo dataset.
2. Create the three new identities below. Enter `Tester2026!` in both password fields. Leave phone blank for the customer and market manager. If a sample email or workspace was used in an earlier run, append a unique suffix to the address local part and workspace name. If the explicit vendor phone is already in use, pick an unused fictional number in `+1 (617) 555-0100` through `+1 (617) 555-0199`.
3. After each creation, expect a new row at the top of the table with **Verified (simulated)**. The two blank-phone accounts should have distinct fictional numbers. Use **Copy Login Details** before closing, and keep the SuperAdmin window open. Use separate browser profiles or sign out between test accounts to test each login independently.
