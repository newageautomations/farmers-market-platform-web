# Cloudflare Quick Tunnel demo readiness audit

## Assessment

A single temporary HTTPS URL is feasible in principle, but the application is **not ready to use through a tunnel unchanged**. One tunnel can point to a loopback-only reverse proxy that dispatches the browser-facing routes to the existing local servers. The difficult part is application behavior: account, admin, and tenant storefronts currently use distinct origins, while one Quick Tunnel supplies one public hostname. A proxy alone cannot preserve those origin-based distinctions. Supporting all requested roles and multiple storefronts under that hostname requires bounded application changes and verification, not just environment variables.

This is a static code audit. No server, browser, build, or test was run. Actual tunnel, host-header, cookie, upload, and sign-in behavior remains to be verified during implementation. Quick Tunnel requires `cloudflared` on the Windows host, not the Mac; the URL changes on restart and is publicly reachable by anyone who has it.

## Current architecture

| Local service | Role | Public exposure needed |
| --- | --- | --- |
| Astro SSR, `127.0.0.1:4321` | Customer, central account and host-selected market/vendor storefronts | Selected page and same-origin BFF routes |
| Vite admin, `127.0.0.1:4322` | Vendor, market-manager and platform admin SPA | Selected SPA paths and required static assets |
| Vendure, port `3000` | Shop and Admin GraphQL, assets, account bridge and other endpoints | Browser needs a restricted Admin API and assets; SSR can call Shop API and bridge privately |
| PostgreSQL, normally loopback `5432`, `vendure_demo_market_ops` | Persistent demo data | None |
| Worker and document scanner | Background work and upload scanning | None; demo `serve` starts the scanner via Docker |

Start the persistent environment only with the web repository's `demo:market-operations:serve`, `worker`, `admin`, and `storefront` scripts. They intentionally select the persistent demo database and local safety policy. The demo runner disables most job queues; features requiring asynchronous processing should be checked individually. See `scripts/demo-market-operations.ts` and the backend's `scripts/market-operations-demo/run.ts` and `environment.ts`.

Astro resolves a storefront from the request authority against the backend and requires a valid storefront and channel. The central account is recognized by exact `PLATFORM_ACCOUNT_ORIGIN`; local examples use `auth.platform.localhost:4321`, tenant-specific `*.localhost:4321`, and admin `localhost:4322`. Admin routes include `/vendor`, `/market`, `/platform`, and `/auth/account`; Astro also owns paths such as `/account`, `/auth/callback`, `/api`, and public storefront pages. Some paths, notably vendor application routes, need an explicit routing inventory before proxy rules are chosen. A single public host cannot represent multiple host-selected tenants without a deliberate tenant selector and path-aware URL generation, or a deliberately limited single-storefront demo. Central-origin detection currently skips storefront resolution for the whole origin, so simply setting all origins to the same URL also breaks storefront context.

## What works and what breaks

- SSR already calls the Shop API and the secret-protected account bridge server-to-server over loopback. Browser-facing customer operations generally use Astro's same-origin `/api` routes. These are useful existing boundaries and need no direct public database or worker access.
- Admin receives `PUBLIC_ADMIN_API_URL` as a Vite compile-time constant and calls Vendure from the browser. The demo script overrides it and `SHOP_API_URL` with `http://localhost:3000/...`; on the Mac, localhost means the Mac, and HTTP from HTTPS also triggers mixed-content restrictions. Use a public same-origin HTTPS Admin API URL while retaining the private loopback SSR endpoint. The backend demo currently sets CORS to `http://localhost:4322`; same-origin proxying avoids browser CORS, but backend origin checks still require correct configuration.
- No application WebSocket endpoint was found in the inspected frontend API code. Vite development HMR uses a WebSocket and may require proxy upgrade and public `wss` configuration; it is not evidence that application features use WebSockets. Prefer a local production-like static admin serving arrangement if compatible with the guarded demo, or explicitly configure and restrict the dev server. Verify any additional live feature individually.
- Account login uses exact origin checks, one-time correlated handoffs, host-only cookies, and separate admin and storefront callbacks. The backend validates the destination against the configured admin origin or a registered storefront canonical origin; workspace and customer links can be generated from those origins. The local demo's frontend `scripts/local-account-environment.ts` and backend `scripts/market-operations-demo/environment.ts` reject non-local account/admin origins. A new random tunnel URL therefore needs coordinated, explicitly guarded configuration in both processes, plus path-aware routing and tenant/handoff handling. Do not bypass authorization or handoff validation.
- HTTPS terminates before the local HTTP services. Astro has origin checking and explicitly does not trust forwarded headers for security decisions; middleware compares the request Origin with `context.url.origin`. A proxy must establish a verified public request origin for Astro without accepting arbitrary client-supplied forwarded headers. Host rewriting alone can cause HTTPS/HTTP origin mismatches, failed POSTs, wrong redirects, and incorrect Secure cookie flags. Production mode currently requires native HTTPS and rejects proxy trust, so flipping production flags is not a solution. Vite host validation also needs an explicit tunnel-host allowance, not a wildcard.
- Vendure serves uploads through `/assets`; locally generated absolute asset/canonical URLs and saved `*.localhost` URLs will not resolve from the Mac. Route only required public assets through HTTPS and ensure generated URLs use the current public origin; inspect existing stored URLs and each upload/preview path. Uploads use the Admin API and document scanner, so verify size limits, multipart forwarding, authentication and scan results. Storefront themes permit some localhost image URLs, but the remote browser still cannot load them. Editor preview has explicit admin-origin, iframe and CSP rules and needs separate verification.
- Account verification, invitations, recovery and provider callbacks can produce absolute links or require email/SMS. The guarded demo disables external communication, so do not assume delivery or provider OAuth works remotely. Existing accounts and nonpayment workflows are the practical starting point. Link and asset data must not be silently rewritten in the persistent database.

## Payment isolation

The persistent demo loader defaults `STRIPE_ENABLED`, `SAAS_BILLING_ENABLED`, `SAAS_BILLING_ALLOW_NETWORK`, `POS_ALLOW_NETWORK`, communications and related provider flags to `false`; it rejects unexpected provider settings and installs an outbound network guard. Leave `DEMO_STRIPE_CONNECT_TEST` and QuickBooks sandbox opt-ins off and supply no live provider credentials. Square operates through the POS provider configuration, which the same demo guard refuses or disables. Do not weaken these guards for tunneling. Cash POS remains separately enabled where the existing channel grant and membership allow it. `LOCAL_TEST_PAYMENTS_ENABLED=true` is an optional, separately guarded **no-charge** test payment on the approved database; its default is `false`, and it is not required for nonpayment demonstrations. Existing payment setup or checkout screens may consequently show unavailable states. See backend `scripts/market-operations-demo/environment.ts` and `src/plugins/marketplace-commerce/commerce/local-test-payment-policy.ts`.

## Smallest recommended approach

1. Add an opt-in, local-only demo mode with a loopback-bound reverse proxy in front of the existing services, and point one Quick Tunnel at that proxy. Route explicit Astro and admin paths, the minimum required admin GraphQL endpoint, and public assets. Preserve the normal localhost scripts and origins when the mode is off. Bind backend, proxy and dev servers to loopback where possible and verify firewall bindings.
2. After the tunnel assigns its URL, provide that exact HTTPS origin to the proxy and both application sides. Adapt the existing guarded demo account configuration to accept only this explicitly supplied temporary origin without relaxing database, provider, bridge-secret, or authorization safeguards. Solve request-origin reconstruction at a trusted local boundary, stripping untrusted forwarded headers. Configure admin's browser API URL separately from Astro's loopback API URL. Re-establish the URL and restart/reconfigure affected processes when the tunnel changes.
3. Implement the smallest explicit path-based tenant mapping needed for the demonstration, including canonical links, storefront resolution, account handoffs and workspace switching. Inventory overlapping paths before choosing prefixes; preserve existing permission checks and separate callback semantics. If only one storefront is needed, an explicit fixed demo mapping may reduce scope, but it still must coexist with central account handling on the same origin. Avoid modifying saved tenant domains just to accommodate a transient hostname.
4. Validate end to end from a different network: customer and both workspace roles, login/logout and switching, tenant links, forms, images and uploads, cookie security, HTTPS redirects, and normal localhost behavior. Verify disabled real payment providers and run only appropriate local checks with the persistent database protected.

## Security boundaries

A Quick Tunnel is an internet-facing entry point, not an access-control system. The existing demo has known local credentials, a fixed development cookie secret, dev tooling and a populated database. Replace or isolate demo credentials and secrets, limit data and audience, and add a protective access layer at the proxy if suitable; do not rely on an obscure URL. Restrict methods and paths, preserve authentication, CSRF and tenant authorization, and rate-limit as appropriate. Never forward the account bridge, GraphiQL, development mailbox, provider webhooks/OAuth callbacks, internal health or debugging endpoints, scanner, database, or worker ports. Do not proxy all of port 3000 or expose Vite's development tooling without a deliberate review. Review GraphQL Admin API exposure carefully: it is a real privileged API even if the UI is the intended entry point. Stop the tunnel after the demo.
