# Application filter toolbar redesign

The Submitted Applications page now uses shared tertiary Buttons for All, To review and Awaiting vendor, a permanent debounced search, and the existing Dropdown disclosure card containing the advanced filters. Done closes the card and restores focus. Additional filters produce removable chips and a filter count; search, sort and quick view are excluded from that count. Clear filters resets additional filters and sorting while preserving search and quick view. Clear all removes only additional filters.

Reused components: Dropdown, SearchSelect, SelectField, StatusBadge, Button, Field/Input, DataTable and Pagination. Tabs has an optional change callback, including keyboard changes. SearchSelect has an optional option renderer; existing consumers retain text rendering. Status options, selection indication and status chips render the actual existing StatusBadge, sharing statusTone and semantic presentation without new colors. The other controls remain existing shared selects.

The existing JSON application read input now accepts a quickView constraint. REVIEW selects SUBMITTED and UNDER_REVIEW; VENDOR selects NEEDS_INFO; ALL adds no constraint. This intersects with the selected status and other predicates before database paging/counting. Incompatible combinations intentionally show no matches. No endpoint, dependency, migration, account or test-data changes were introduced.

Files changed: ApplicationSubmissions.tsx, market/dashboard.css, shared SearchSelect.tsx and index.tsx, API market-operations.ts, backend application-review.ts, and the focused application-phase-d component tests.

Verification: six focused component tests cover paging, search/filter combinations, quick views, card closure, semantic status rendering, chips, clearing and review details. Web TypeScript and scoped ESLint pass. Backend production build checked separately. No browser automation or screenshots were used.

Limitations: quick views have no invented counts. The card retains the shared native disclosure interaction rather than adding a new menu controller. Desktop/mobile visual verification remains manual. Existing review, onboarding, server pagination and authorization remain unchanged.

The follow-up layout correction replaces the quick-view tabs with tertiary Buttons and aria-pressed state, removing the tab divider and empty tab panels. The search label remains accessible but visually hidden. The Filters button shares the input control height. The existing Dropdown gained optional controlled open and className props so its trigger can sit beside search while its card expands below the full toolbar. Filters use a two-column grid, stacking below 600px, with actions aligned at the bottom. No query or test-data changes were required for this correction. Six focused tests, web TypeScript and scoped lint passed. Verify the corrected spacing, matching control heights and two-column card on channel 42.

The filter card no longer renders a heading. All statuses is a neutral pinned first option in the existing searchable select, replacing its separate clear button. The shared option type supports an optional pinned flag without changing ordinary option ordering. Quick views share one measured backdrop which slides and resizes between tertiary buttons using the current semantic selected fill and radius. ResizeObserver keeps it aligned when layout changes. The filter card has an entrance expansion/fade animation. Both motions respect reduced-motion preferences. Focused component tests verify the first option, absence of the redundant button/heading and existing filtering interactions; motion appearance remains a manual check.

Closing now uses one shared close handler for Done and the Filters toggle. The card remains mounted during a measured-height collapse/fade, then closes after 240 ms. Focus returns to the trigger and closing content is inert. Reopening cancels a pending close; reduced-motion users close without animated motion. Focused tests cover delayed closure through both controls.
