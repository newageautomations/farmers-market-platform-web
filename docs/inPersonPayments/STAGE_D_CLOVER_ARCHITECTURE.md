# Stage D Clover architecture

Implemented locally on October 19, 2026. Vendure and the existing InPersonPaymentCoordinator remain authoritative for quotes, products, taxes, discounts, capacity, orders, customer identity, financial units, handoff and receipts. Clover is a separate provider below the existing payment adapter. Square's provider, OAuth, devices and webhook implementation are retained.

## Official interface decision

| Option                             | Assessment                                                                                                                                                                                                           | Decision                 |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| REST Pay Display over Clover Cloud | Backend HTTPS requests, OAuth bearer credentials, serial-addressed terminal, original payment retrieval and linked refunds                                                                                           | Selected                 |
| Remote Pay Cloud Connector         | Official JavaScript SDK supports browser and Node WebSockets and more event-driven device interactions. Browser examples require particular care with merchant tokens. Its README currently describes version 4.1.2. | Evaluated, not installed |
| Local network Pay Display          | Device reachability, certificate installation and network trust complicate hosted/browser operation                                                                                                                  | Deferred                 |

The current [REST overview](https://docs.clover.com/dev/docs/rest-pay-overview), [introduction](https://docs.clover.com/dev/docs/rest-pay-intro), [development checklist](https://docs.clover.com/dev/docs/rest-pay-development-basics), [cloud connection guide](https://docs.clover.com/dev/docs/configuring-a-cloud-connection), [request example](https://docs.clover.com/dev/docs/build-a-cloud-connection-request), [official SDK](https://github.com/clover/remote-pay-cloud) and [examples](https://github.com/clover/remote-pay-cloud-examples) were consulted. The live official references continue to document `/connect/v1`; no superseding REST version was found in those references. No unofficial SDK or new package dependency was added.

## Configuration and OAuth

`CloverOptions` is server controlled. App ID and Remote App ID are distinct, required values. RAID is retained in every operation and must be configured for the OAuth app in Clover. The documented REST request does not define a separate RAID header; none is invented. `X-POS-Id` is a separately configured stable register/application identity. Requests include User-Agent, bearer authorization, content type, device serial and the original financial operation's idempotency key.

Only US Sandbox effects are enabled. Production and other region configurations fail closed before network access. Clover documents distinct Production North America, Europe and Latin America hosts in its [OAuth guide](https://docs.clover.com/dev/docs/use-oauth); they are not permitted destinations in this stage. There is no automatic fallback or production opt-in. Further regional and production enablement requires separate qualification.

The backend follows the [high-trust confidential flow](https://docs.clover.com/dev/docs/high-trust-app-auth-flow), using `/oauth/v2/authorize` and JSON `/oauth/v2/token`. PKCE belongs to Clover's low-trust classification and is not substituted for this confidential app. Random state is bound to vendor, owner user, session hash, channel, application, environment, region, exact callback and a ten-minute deadline. State and code hashes are unique and one-time. Vendor integration authority remains `ManageOwnPosIntegrations` through the existing access policy.

For real Sandbox, register an exact HTTPS backend callback ending `/in-person/clover/oauth/callback`. It validates the pending state and app, encrypts the returned code and merchant identity with the existing AES-256-GCM envelope, then issues a no-store/no-referrer redirect to the server-configured dashboard return URL. Only state travels back to the original local dashboard. `finishOwnCloverConnection` requires the initiating authenticated session before decrypting and consuming the code. This avoids cross-origin session loss when a developer later supplies a secure callback tunnel. The tunnel and publicly registered URL are external prerequisites, not created by Stage D.

Access/refresh ciphertext uses Stage C's existing `SquareTokenEnvelope` implementation with independent Clover keys and Clover-specific associated data containing application, environment, region, vendor, channel, connection and merchant. No second encryption implementation was introduced. Tokens, codes and secrets are omitted from settings, receipts, browser bundles and logs. Provider token lifetimes are read from Unix expiration timestamps.

Refresh uses an atomic durable lease and revision check, with no database transaction held across network IO. The encrypted old refresh token and an uncertainty marker commit before `/oauth/v2/refresh`. Concurrent callers cannot consume the same token. A lost response or restart uses `/oauth/v2/recovery` with the preceding token and app secret, following Clover's [single-use token and recovery guidance](https://docs.clover.com/dev/docs/refresh-access-tokens). Recovery rejection requires reconnection; it never blindly resends a possibly consumed refresh token. The documented recovery validity is up to two weeks. An interrupted marker from before a request was sent may conservatively require reconnection.

A merchant cannot be reassigned to an unrelated vendor. Reauthorization can replace credentials for the same immutable merchant while recovering pending payments. Disconnect requires no unresolved operations, removes local ciphertext and retains history. Remote revocation is performed by uninstalling/disconnecting the app in Clover's merchant dashboard; no unsupported revoke API is invented. Provider 401s and authenticated app-deletion notifications mark authorization revoked.

Provider authorization failures are guarded by the exact credential revision used by that request. A delayed 401 from an older token cannot mark a newer same-merchant reconnection revoked. The concurrent reconnection race is fixture tested.

## Devices and preparation

Devices are selected by actual serial, verified through [merchant-provisioned devices](https://docs.clover.com/dev/reference/devicegetmerchantdevices). Registration validates the connected merchant and supported Flex/Mini/Compact family. First-generation Flex `C041/C042` and Mini `C030/C031` serial prefixes are rejected conservatively following Clover's [2026 end-of-app-update announcement](https://docs.clover.com/dev/docs/announcement-end-of-app-update-gen-1-devices). A family name alone does not establish firmware, regional or physical qualification.

Friendly labels, default selection, soft removal, last connectivity check and unverified availability are supported. Registration does not assert that Cloud Pay Display is running. The [ping endpoint](https://docs.clover.com/dev/reference/ping_device) establishes reachability at a timestamp, not continuing availability or payment readiness. Unresolved operations show busy and prevent removal or conflicting use. A partial unique index reserves each terminal, including linked refunds, while preparation takes short connection/device row locks. Historical operation identities cannot be changed or deleted.

The existing coordinator validates quote, actor, vendor, ownership, authoritative amounts, market context and capacity. It commits a durable attempt and original provider operation before external IO. Clover preparation freezes merchant, application, RAID, device UUID/serial, POS identity, environment, original reference and operation. A durable dispatch marker prevents another create after an interrupted response. Conservative uncertainty is preferred if a crash occurred between that marker and the first provider request.

## Sales, evidence and cancellation

The adapter uses the official [sale request](https://docs.clover.com/dev/reference/pay) with exact integer USD amount, `final: true`, zero tip, no cashback, offline payment disabled and card-present EMV/NFC/magstripe methods. Manual entry and vaulting are excluded. Vendure cart/catalog records are not synchronized. Optional Clover order-display APIs are deferred.

Initiation supplies locators only. The adapter independently retrieves by [external payment ID](https://docs.clover.com/dev/reference/get_payment_by_external_payment_id), by [payment ID](https://docs.clover.com/dev/reference/get_payment), and through the original merchant's v3 payment endpoint with device/card-transaction context. It verifies ID, original random reference, device UUID, merchant/USD currency, exact amount, SUCCESS, online card entry, CLOSED/AUTH state and zero additional tips/cashback/charges. Returned app tracking is checked when available; frozen app and RAID configuration must remain unchanged. Missing required evidence stays uncertain. Merchant currency supplies the currency boundary where Clover omits currency from its payment object. Real provider field/expansion availability still needs Sandbox/hardware qualification.

Only ProviderFactsService's independent verified-result boundary feeds native completion. No browser success mutation exists. Completed facts permit exactly the original native payment, capacity conversion and physical handoff. Mismatches retain safe scalar observations, references, append-only fact timestamps and inventory. Capture evidence surviving a native finalization failure is reused for that original order.

The supported [device cancellation](https://docs.clover.com/dev/docs/canceling-the-current-action) is a request, not proof of no charge. Retrieval determines whether capture won the race. No pending cancellation automatically releases capacity. Settled payments use an authorized original-unit refund. Arbitrary draft cancellation, terminal cancellation and settled refunds remain distinct; no automatic payment void or reset-device operation is exposed.

## Refunds and conservative limits

RefundCoordinator supplies immutable original financial units and their tax/discount allocation. The adapter calls [linked REST Pay refunds](https://docs.clover.com/dev/reference/refund), always specifying the exact native refund amount with `fullRefund: false`, including when all remaining units are selected. Independent [merchant refund retrieval](https://docs.clover.com/dev/reference/paygetrefund-3) verifies refund ID, original payment, amount, tip and non-voided result. The synchronous acknowledgement is durable, and additional reported status must indicate completion before financial settlement. Pending, mismatched or unavailable evidence retains original reservations. No automatic restock is introduced.

If the response was lost before its refund ID was durably received, the adapter neither resends nor guesses from timestamps/amounts. Clover's [refund FAQ](https://docs.clover.com/dev/docs/payments-and-refunds-faqs) says the original idempotency key is not exposed through normal refund retrieval. This is an explicit reconciliation blocker requiring independently correlated provider evidence and future reviewed remediation. There is no force-success or arbitrary attach-refund-ID endpoint. Ordinary failed/unknown refunds do not automatically create a replacement operation. Controlled fixtures exercise pending, later completion, voided failure and lost-ID quarantine; these are not claims about real Sandbox behavior.

## Webhooks and polling

The optional receiver implements Clover's [general REST webhook](https://docs.clover.com/dev/docs/webhooks) format: configured `X-Clover-Auth` compared using fixed-size constant-time digests, correct `appId`, connected merchant, bounded P/A resource events and timestamp validation. Receipts retain resource identity and digest without raw payloads. Payment notifications trigger existing stored-actor recovery and provider retrieval. Duplicate/out-of-order deliveries cannot directly finalize payments. App deletion is accepted only for the exact configured app and is ordered against connection updates.

There is no Square signature imitation or Hosted Checkout signature handling. Clover's external webhook setup/verification handshake and live delivery have not been configured or qualified. The receiver does not expose or log unauthenticated setup codes. Provider polling and the existing bounded recovery sweep remain necessary, including when webhook delivery is absent. No separate documented refund-completion notification is assumed.

## Data and UI boundaries

`1793100000000-CloverInPerson.ts` adds Clover connection, encrypted secret, OAuth, device, operation and webhook tables, indexes and immutable ownership guards. Existing allowed provider/method vocabularies gain Clover without removing Square, cash or simulator constraints. The downgrade refuses to erase history. Only disposable databases were migrated.

Frontend settings use the existing dashboard and approved Card, Badge, Button, Dialog, Field, Input, Alert and Spinner. The new controller is necessary because Clover's OAuth/device lifecycle differs from Square's pairing/location model. POS method selection, receipt, recovery and refund compositions are extended in place. Dialogs use the existing payment-dialog class, design tokens and action contract. There are no new primitives, heading labels, breadcrumbs, UI libraries or cart/refund engines. Customer/guest/market attribution and the in-person loyalty exclusion remain coordinator-owned.
