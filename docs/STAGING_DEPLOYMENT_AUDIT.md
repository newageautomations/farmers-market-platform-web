# Staging deployment readiness audit

## Executive summary

**Overall readiness is implementation required.** Railway, PostgreSQL, Cloudflare DNS, R2, GitHub, and a dedicated Stripe Sandbox fit the platform. The checked-in backend has independent API and worker entry points and PostgreSQL-backed jobs. The frontend build produces both a tenant-aware Astro SSR server and a separate React Admin SPA.

- **Before hosted deployment:** Adapt the production frontend launchers and request authority model for hosted TLS. Prove a routing path that preserves tenant authority on SSR-to-API storefront resolution. Add an operator-owned way to register public storefront hostnames and a migration-only release command.
- **Before external testing:** Enforce tester and recipient admission, staging-wide noindex, durable storage, and private scanning for enabled uploads. Resolve the conflict between hardened startup and the existing Stripe staging mode. Add narrow Stripe browser CSP allowances and qualify actual Sandbox payment flows.
- **Additional services:** Host the Admin SPA, run a private ClamAV service if documents are in scope, and use controlled Resend and Twilio delivery for email and phone flows. Reserve backup storage and basic monitoring. The installed SQL queue and scheduler do not require Redis.

This is a source audit of the current working trees, which both contain pre-existing local changes. The referenced behavior needs to be present in the exact revisions selected for hosted deployment. Provider routing, certificates, private networking, plans, and integration capabilities remain subject to hosted verification. No services, tests, builds, database commands, or provider operations were run.

## Recommended hosted staging architecture

| Component | Initial staging arrangement |
| --- | --- |
| Cloudflare | Register a temporary domain, manage DNS and validated TLS, and apply host/path admission and cache rules. Keep all participating browser hosts under one registrable domain. |
| Railway web | One Astro SSR service for central accounts and tenant hosts, plus a small static Admin service with SPA fallback and the existing security policy. These can build from the same web revision. |
| Railway backend | One API and one private worker from the same immutable backend revision. Expose only the browser API and necessary provider ingress through an approved route policy. |
| Railway PostgreSQL | One private staging-only database on PostgreSQL 17, with staging credentials and backups. Provision/reset policies for disposable CI databases remain independent. |
| Cloudflare R2 | Separate public-media and private-document storage boundaries. Keep Vendure image processing available where URLs require it. A Railway volume can bridge the filesystem-backed implementation for a single writer while adapters are completed. |
| Private scanner and communications | ClamAV for document/receipt workflows. Use an isolated Resend identity and a Twilio project/service with tester-recipient controls for flows requiring delivery. |
| Stripe and GitHub | Dedicated Stripe Sandbox and Connect application identity. Use approved GitHub revisions, one coordinated staging release, and separate staging and future production secrets. |

Use one replica per service initially. If the chosen Railway ingress cannot preserve tenant authority or provide the required origin controls, add a narrow trusted gateway at the routing boundary. Start with explicit pilot tenant hostnames if wildcard ingress is unavailable. Either option still requires the resolver transport described below.

**Tenant registration.** `platform_storefront.hostname` is nullable and unique, independent of the storefront key and route slug. Current vendor and market provision/configure services do not assign it. Local fixtures populate it explicitly, including `.localhost` and `.platform.localhost` names. A clean staging pilot needs controlled registration for each tenant. A copied site needs hostname regeneration plus updates to embedded links, callbacks and asset references. Implement a normalized single-label assignment under the staging zone with collision checks across both tenant types and reserved names such as `admin`, `auth`, `api`, `assets` and any gateway or operator names. Retain the exact active record, active subject, channel eligibility and unique database index. DNS wildcarding alone neither assigns hostnames nor activates storefronts. An unknown, invalid or inactive tenant must map to the existing unavailable/not-found path and never another tenant. Treat apex, reserved and provider-issued hosts explicitly at ingress. [Hostname migration](../../farmers-market-platform/src/migrations/1791230000000-StorefrontPublicHostname.ts), [vendor write](../../farmers-market-platform/src/plugins/platform-identity/identity.service.ts), [market write](../../farmers-market-platform/src/plugins/marketplace-commerce/market-storefront.service.ts), [resolver](../../farmers-market-platform/src/plugins/platform-identity/public-storefront.controller.ts).

**TLS and private calls.** The backend requires `req.secure` and the canonical wire Host on non-health paths, with a tenant Host exception for resolution. It trusts an explicit proxy CIDR allowlist, disabled by default. Astro currently rejects non-HTTPS request URLs, has an empty forwarded-domain allowlist, and rejects configured proxy trust. Simply removing the certificate paths will leave an HTTP origin that fails on real requests. Phase B must either retain TLS through to the app with supported ingress or reconstruct HTTPS only from a verified ingress connection with controlled headers. Preserve Host validation, strict equality for state-changing Origin, HSTS and exact destinations. Verify the immediate peer, how forwarded protocol/client-IP chains are generated and overwritten, and the actual direct-origin exposure. Keep provider-issued origin domains disabled or deny their traffic at the protected origin. Align the API proxy allowlist with actual peers. Avoid trusting network-wide forwarding and use validated origin TLS in the chosen Cloudflare arrangement.

Astro can configure public Admin and Shop URLs independently. It cannot currently take a private HTTP Shop endpoint in hardened mode. Resolver code dials the Shop origin with that origin's TLS server name but puts the **tenant** in the wire `Host`; the backend resolves that Host. A CDN or managed router that routes by Host can send this request back to Astro or reject the host/TLS pairing. A standalone public API URL does not solve it. Prefer a private, authenticated SSR-to-API route that carries canonical API transport authority and an explicitly authenticated normalized tenant value, or prove a controlled private route that preserves the current resolver contract. Scope any new hostname field to the trusted SSR/gateway and preserve backend checks. Also route Shop GraphQL, the account bridge, vendor terms revision reads and preview authorization privately where feasible. Both public and private targets need clear routing and TLS policy. PostgreSQL, ClamAV and worker have no public network requirement. [SSR resolver transport](../packages/storefront-core/src/backend.ts), [SSR middleware](../apps/storefront/src/middleware.ts), [API guards](../../farmers-market-platform/src/production-http.ts).

**Session and request controls.** Central `platform-unified-account` stays on the auth host. Vendor and market Admin workspaces exchange a single-use, correlated, actor-bound handoff via `/auth/account` and the credentialed Admin API. Shop handoffs use the tenant's `/auth/callback` and Astro sets its first-party session. Separate Admin and Shop cookies are host-only, Secure in production, HttpOnly and SameSite=Lax, with seven-day session bounds. Continuation state has shorter lifetimes. The Admin correlation/destination cookies are client-readable by design and path-scoped. Keep Admin and API HTTPS on the same site so credentialed CORS and these cookies work. Preserve exact Admin-only CORS, browser mutation/GraphQL CSRF checks, server bridge boundaries, safe return URLs and recipient workspace reauthorization. Global sign-out and password reset revoke backend sessions and outstanding capabilities across surfaces. The top-level redirect model works without parent-domain cookies. Keep API and Astro rate limits and durable account budgets; central and tenant bridges can concentrate traffic behind one SSR egress IP, so verify rate attribution and thresholds through the final topology. Production disables GraphiQL, API introspection/debug, mailbox and scaffold Dashboard access. Keep fixture-only pages disabled in hosted builds. ## Database and migration strategy

## Storefront SSR and caching requirements

Astro renders each storefront request after host resolution. The backend projects current active tenant, live website and published appearance from PostgreSQL, and commerce queries use the resolved channel context. A request-local WeakMap can deduplicate catalog reads within one SSR request. No cross-request HTML or tenant-context cache was found. Publish changes the durable live/published state seen on the next fresh request, so there is no storefront page purge mechanism. Vendure SQL-backed search projections and AssetServer transformed-image caches are separate from page rendering.

The editor posts a bounded draft and short-lived authorization token to the tenant's preview endpoint. SSR checks the backend authorization for the same tenant, renders using request-local preview state, and keeps it no-store. Market Day landing is request-dependent on real market context, active state/time, and the regular storefront override. Market-Day refresh calls are no-store; keep them and schedule-sensitive availability out of shared caches. Restarts clear local throttling/memoization and do not remove the database's published state. Multiple Astro replicas have no evident HTML publication consistency problem under this no-store model; confirm shared keys, consistent builds, rate aggregation and real timing before scaling.

Bypass Cloudflare shared caching for SSR HTML, errors, Admin/account routes, all dynamic APIs, any response with session state or `Set-Cookie`, carts, checkout, document downloads, previews, provider ingress and health. Honor origin `private, no-store`; avoid a catch-all cache rule. Cache only explicitly approved immutable hashed build assets and public media. Include full hostname and any allowed image transformation query in cache keys, and use versioned media keys or purge on removal/replacement. If edge admission covers an asset, keep that asset out of public cache.
