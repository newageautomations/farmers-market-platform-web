# Component usage guide

Rental image dialogs opt into `CategoryImageField.stockImages` with the local `rental-stock.ts` collection. Only `RentalWizard` passes this prop, so other image dialogs do not show Stock Images. The shared tabs, image grid, button and dialog contracts are reused. Stock selection references the bundled image directly, with `imageStockId` and its absolute preview URL in rental details JSON; `imageAssetId` remains null. No upload or personal-library copy occurs. Theme selections retain their existing theme asset reference. My Images is built only from library reads and personal uploads, never from a selected-image fallback. Errors remain in the picker and busy dismissal stays guarded. The collection now contains ten matching blank-background equipment images, one per seeded rental type, with no credit or generation labels in the UI. Production prompts and asset paths are recorded in `docs/RENTAL_EQUIPMENT_IMAGES.md`. Every Stock, My Images and Theme Images tile reuses `IconButton` for an independent Enlarge action and the shared Dialog for a contained full-size preview stacked above the picker. Previewing does not choose or upload an image. Closing restores the existing picker and its focus. No new UI primitive is required, and saved rentals are not automatically changed.

Rental equipment at `/market/rentals` composes `WorkspaceFrame`, `MarketsSummary`, Farmstand search/selects/table/buttons and `MarketsPagination`, matching Occurrences and Applications. `RentalWizard` is a feature controller because no shared component owns rental validation, pricing, stock limits or revision-aware saves. It reuses `Dialog`, `WizardProgress`, `useWizardDialogHeight`, the reward wizard stage/review/success presentation and `CategoryImageField` for library selection and PNG/JPEG upload. Create and edit both stay in the modal; legacy `/market/rentals/new` links open it over the inventory. Image metadata is optional in the existing rental details JSON, with no migration. The existing channel-scoped storefront media API requires `ManageMarketStorefront`; rental management still requires `ManageOwnMarketApplications`, and per-date allocation reads retain `ReadOwnMarketAssignments`. The image is presentation metadata and has no billing or stock authority.

Market Vendors at `/market/vendors` is one list of every business at the market: platform Vendor memberships and external directory businesses (`VendorsWorkspace.tsx`). It composes `WorkspaceFrame`, `MarketsSummary`, Farmstand search/selects/table, the Applications row selection and side panel, and `MarketsPagination`, matching Rentals, Occurrences and Applications. The former `/market/directory` routes open this list (`/new` opens Add business) and the Vendor Directory sidebar entry is removed. Add business opens `BusinessWizard` in the shared Dialog, reusing `WizardProgress`, `useWizardDialogHeight` and the reward wizard type-choice, stage, review and success presentation: choose Platform Vendor (search eligible Vendors, always added as a pending membership because the backend requires Vendor consent before approval, optional private notes) or External business (business, contact, review). Platform Vendors own their business details: managers can only change their membership and private notes, and the backend `SAVE_DIRECTORY` rejects contact changes on verified linked records (`PLATFORM_VENDOR_DETAILS_READ_ONLY`). Private notes use the additive `SAVE_VENDOR_NOTES` operations command and `market_vendor_note` table (migration `MarketVendorNotes1796200000000`), returned as `vendorNotes` by the DIRECTORY read, and edited in `VendorNotesDialog`. Compliance (`vendor-compliance.tsx`) shows a meter (the Occurrences booth-meter presentation) and each outstanding request with `DocumentStatus`, from the compliance summary plus the read-only `ownComplianceDocuments` read exposed as `MarketService.documents` with `ReadOwnDocuments`. Vendor pages at `/market/vendors/memberships/:id` reuse the application/occurrence detail layout (`Panel`, `Fact`) with padded panel bodies and `WorkspaceMenu` views (Overview, Market dates, Listing approvals, Products by date) that switch in place under the menu with hash links, as in Loyalty (`#market-dates`, `#listings`, `#products-by-date`; legacy `/market/vendors/:tab/:id` links open the same view). Forms keep their `CommandForm` controllers with Farmstand selects and the new optional market `CommandForm` `submitClassName` slot. Listing review opens `ListingReview`: the Vendor's read-only `HarvestProductPreview` (extracted from `ProductSetupPreview`, with its styles moved to `harvest-product-preview.css`) plus Approve and Deny (Deny records the existing `withdrawn` status), backed by the additive manager read `ownMarketListingPreview`, scoped to the Market's memberships and the Vendor's own product. Market dates filters by the Market Occurrences period presets (Custom date range opens the shared `OrdersDateRange` modal) and participation status; Listing approvals filters by approval and publication; Products by date filters by market date and status and is ordered by market date. Each view reads every page of its records so filters cover them all, then pages ten at a time with `MarketsPagination`. Compliance items show only their tone, name, due date while missing, and status. Products by date lists the Vendor's occurrence offerings (which approved products it sells on each market date, with preorder availability and an optional sales cap). The Vendor owns these offerings: a Market can only disable an existing offering (with confirmation) or re-enable a disabled one. It cannot add a product to a date, change preorders or the sales cap, or rematerialize the preorder window, and the backend rejects those Market writes with `MARKET_OFFERING_DISABLE_ONLY`. No new UI primitive is introduced.

Booth counts use the existing booth schedule read; nothing is shown for dates without a layout. Schedule, single-date, edit and cancel commands keep `CommandForm`. The detail page at `/market/occurrences/:id` reuses the vendor detail `Panel`/`Fact` layout. See [the registry](UI_COMPONENTS.md#market-occurrences-presentation-november-6-2026).

Market Operations at `/market/operations` reuses the same list composition (summary, filters, table, side panel, pagination, `BoothCell`/`BoothMeter` exported from `occurrences.tsx`) with a Readiness column, and `/market/operations/:id` reuses the detail layout with `ReadinessChecklistPanel` as the main column. Documents at `/vendor/documents` and `/market/documents` composes `WorkspaceFrame` (heading and Upload document action), TAB-01 `Tabs` with the `workspace-menu` class and Farmstand icons (keeping tab roles and `?view=` links), `SettingsPanel` sections (now with an optional `actions` heading slot; its CSS lives in `settings/settings-panel.css`), `FarmstandButton`, `FarmstandTable`, `FarmstandPagination` and `MarketsSummary`. The workspace root carries `farmstand-controls`, which gives every dialog inside it, including the shared document upload/share dialogs, the Farmstand control presentation. Library, request and agreement cards use `DocumentCard` over RecordCard; dialog facts use `DocumentFacts`. No new primitive, API, migration or database change is introduced.

The vendor Dashboard at `/vendor` (`VendorDashboard.tsx`, replacing the former vendor Overview) composes `WorkspaceFrame`, `MarketsSummary`, Farmstand panels and controls, the Markets next-date panel and the finance `FinancialGraph`/`FinanceDonut` (with the new optional `legend` and `unitLabel` props). Sections: Urgent requests (rendered only when items exist: expired or expiring library documents, missing/rejected/expired required Market document requests, upcoming dates within 14 days without an attendance response, open booth invoices, applications in `NEEDS_INFO` and Market link requests), key metrics compared with the previous equal period, next upcoming market, This week (tasks derived from records, never stored checkmarks), sales over time (gross sales only, drawn as a short line through `FinancialGraph`'s opt-in `lines` and `height` props), sales by channel and by market, top customers (ranked by net spending in the period from CRM purchase history, CRM grant only, bounded to the 60 most recently active customers), recent orders (customer, total and date; names come from CRM history only with the CRM grant, or the finance-gated in-person receipt) and top products. Every section reads under its own permission, so a missing grant or failed read affects only that section. Derivations live in `dashboard-data.ts`. The page is an 8-column grid of 156px rows (`dashboard-grid.ts`); each section has a cell in grid units plus size limits in `dashboardWidgets` (for example Sales over time defaults to 4×2 and may grow to 8×3; the donut charts default to 2×2 and stop at half width, 4 columns). Sections read their cell through a size context and container queries: donuts switch to a landscape layout (ring beside a larger key) in wide cells, Next upcoming market adds an Also coming up column when wide or rows when tall, ranked lists use two columns from four units wide, and Sales over time draws its line at the cell's height. Urgent requests and Key metrics are full-width bands: on the page they take their content's height (Urgent shows four cards and View all expands it downward) and split the grid into runs above and below them, though the editor draws them one row tall. Hidden, unavailable or empty sections (Urgent requests with nothing urgent) leave no hole: the rest settle upward. Under 1080px the grid flows in two columns, and one under 600px. Customize (`DashboardLayoutEditor.tsx`, a shared wide Dialog) shows the same grid at a reduced scale: drag a section to move it (sections it lands on move down), drag any corner to resize it, keeping the opposite corner fixed (neighbours beside it narrow to their minimum width first, then move down), and hide or add sections back; arrow keys move a focused section and Shift with arrow keys resizes it. The editor uses pointer events and a small pure grid engine rather than a grid library; the arrangement (grid cells, hidden sections) and reporting period are a per-account preference in the user-scoped `vendorDashboard.layout` settings-store field (`dashboard-layout.ts`, `createVendorDashboardLayoutApi`), validated by the backend and normalized on read so new sections appear automatically. Finance sale/refund activity and order transactions now include an additive `channel` (`DIRECT_VENDOR`, `MARKET_OCCURRENCE` or `IN_PERSON`). No migration is required.

Settings at `/vendor/settings`, `/market/settings` and `/platform/settings` is one workspace per role (`apps/admin/src/settings/SettingsWorkspace.tsx`), replacing the former Settings card stack and the separate Integrations pages. It composes `WorkspaceFrame` (the Markets heading and `WorkspaceMenu` route tabs, now shared with Finances and vendor Markets) and one `SettingsPanel` per section. Tabs are real routes: Vendor `/vendor/settings` (Preferences), `/notifications`, `/taxes`, `/payments` (Marketplace Stripe Connect, Square and Clover sections) and `/pos`; Market `/market/settings` (Market configuration), `/preferences` and `/notifications`; Platform `/platform/settings` (Preferences) and `/integrations`. `canonicalSettingsPath` redirects `/vendor/integrations`, `/vendor/integrations/payments`, `/vendor/integrations/pos` and `/platform/integrations` to their tabs. The OAuth return routes `/vendor/settings/payments` (Square), `/vendor/settings/clover-return` and `/vendor/pos/square-return` are unchanged. To place an existing card-based controller in a Settings section, pass its `embedded` prop so the panel is the only outline, and pass the owning module wrapper through `SettingsPanel`'s `module` prop rather than adding form styles. Panel bodies carry `farmstand-controls`, so ordinary shared buttons, inputs and selects inside them take the Farmstand presentation; use that class instead of section-specific control styles. Under 600px the Settings menu wraps onto rows of three. Subscription stays its own sidebar entry, and QuickBooks stays in Finances. No new primitive, API, migration or database change is introduced.

Finances at `/vendor/finances` and `/market/finances` is one workspace (`apps/admin/src/finance/Finances.tsx`) composing the Markets heading, `WorkspaceMenu` route tabs, one reporting-period FarmstandPanel shared by every view, `MarketsSummary` KPI cards, Farmstand panels, tables, search/selects and `MarketsPagination`. `FinanceOverview`, `FinanceTransactions` (list plus always-open details panel) and `FinanceExpenses` (list plus spending summary; rows open the existing `ExpenseDialog`) are feature compositions split from the former single controller; no shared component supplies signed finance reports with these drilldowns. The tabs replace the former sidebar sub-items and in-page link bar; Add Expense and Export Report sit in the heading. The former Analytics pages are now `VendorSalesInsights` and the market `MarketAnalytics` activity panel, rendered on the overview for the selected period and gated by their own analytics grants, so analytics-only roles still reach the overview without finance reads; `/vendor/analytics` and `/market/analytics` open it. Market Booth billing is the Booth invoices tab, reusing the existing operations billing controller; `/market/booth-billing` opens that tab. The platform plan page is labelled Subscription. `useResettingState` restarts paging when filters or periods change without reset effects. No new primitive, API, migration or database change is introduced.

Finance presentation refinement: AdminShell keys every finance route as one workspace, so the heading actions, options read and reporting period persist across tabs. Loading indicators inside the workspace stay invisible for their first 500ms (CSS only, no read-state change). Custom periods use the existing `OrdersDateRange` calendar dialog behind the Farmstand period select, as in Loyalty. Graph metrics use `FinanceMetricSelect`, a feature composition of the shared native `Dropdown` and `Checkbox` presented like a Farmstand select; the Farmstand select is single-value and `SearchableMultiSelect` is a search combobox in another control family. Graph controls share one 36px row. The SVG adapter now uses rounded axis ticks with compact money labels, rounded diverging bars with gradients, a monotone profit line with an area fill, whole-column pointer targets with one multi-series tooltip, and donuts with a track and exact filled ring segments: straight edges offset half a gap from each boundary so gaps stay a constant width from the inner to the outer edge, true corner fillets that shrink to fit narrow slices, and a minimum visible share (taken proportionally from larger slices, never changing reported values) so small slices never touch. Slices grow outward on focus or hover, and their card appears beside the ring on the slice's side with a leader line. The entrance animation starts when the donut scrolls into view and is skipped under reduced motion. `FinanceMetricSelect` uses the Farmstand select's trigger geometry and left chevron, the `::picker(select)` surface, option padding and hover/selected tints, and the same 150ms fade/slide on open and close. Period and graph controls share a 36px height. A missing prior-week baseline is neutral grey. Vendor transaction details link to the existing `/vendor/orders/:id` page; market managers and booth payments have no order destination. Earlier donut-legend and chart-standard decisions are unchanged.

Ordinary buttons, form fields, selects, cards, section headings and aligned filters:

```tsx
import type { FormEvent } from 'react';
import {
  Button,
  Card,
  Field,
  Input,
  SelectField,
  SectionHeader,
} from '@market/ui';

export function SearchFilters({
  onApply,
}: {
  onApply: (query: string, visibility: string) => void;
}) {
  function submit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    const data = new FormData(event.currentTarget);
    onApply(String(data.get('q') ?? ''), String(data.get('visibility') ?? ''));
  }
  return (
    <Card as="section" aria-labelledby="filter-title">
      <SectionHeader title="Filter records" id="filter-title" />
      <form className="ui-control-row" onSubmit={submit}>
        <Field id="record-query" label="Search records">
          <Input id="record-query" name="q" type="search" />
        </Field>
        <SelectField
          id="record-visibility"
          name="visibility"
          label="Visibility"
        >
          <option value="">All visibility</option>
          <option value="visible">Visible</option>
          <option value="hidden">Hidden</option>
        </SelectField>
        <div className="ui-field-action">
          <Button type="submit">Search</Button>
        </div>
        <div className="ui-field-action">
          <Button type="reset" variant="secondary">
            Reset
          </Button>
        </div>
      </form>
    </Card>
  );
}
```

The sample option values are owned by this example's callback. Real features must keep their existing backend identifiers, allowed values, validation and paging resets. `SelectField` is optional by default; set `required` only when the feature requires it. `Field` does not automatically associate errors for arbitrary children: supply `aria-invalid` and `aria-describedby` on `Input` when needed. `SelectField` supplies its error association. `Input` applies the existing name-based `inputContract`; inspect that contract before choosing field names or overriding native constraints.

```tsx

  busy,
  onClose,
  onSave,
  beforeClose,

  busy: boolean;

```
